# План разработки HTML-системы провайдеров

Дата: 17 сентября 2026 года.

Статус: предложение к реализации. Решения, обозначенные как предлагаемые, требуют согласования контракта перед разработкой соответствующего этапа.

## 1. Основания и целевая модель

План учитывает:

- `HTML_SITE_SERVICE_ARCHITECTURE_RU_UPDATED-1.md`;
- `HTML_SITE_BACKEND_SECURITY_RU.md`;
- фактическую реализацию VFSv2 в текущем репозитории;
- уточнение: отдельный scope для каждого сайта, отдельное подключение для каждого создателя контента, дерево сайта хранится и строится отдельно.

Под создателем понимается пользователь или сервис, загружающий контент.

```text
Scope сайта
├── html@подключение-создателя-A
│   └── контент создателя A
└── html@подключение-создателя-B
    └── контент создателя B

Отдельный сервис структуры
└── дерево сайта и ссылки на контент
```

Каталоги внутри подключения организуют файлы. Они не определяют дерево страниц или вложенность блоков.

| Компонент | Ответственность |
| --- | --- |
| Управление сайтами | Связь сайта со scope, участники, создание подключений |
| HTML Provider | VFS-представление контента одного подключения |
| ContentService | Создание, изменение и удаление контента |
| RenderService | Получение представления блока |
| HTML Store | Контент, метаданные, версии |
| Внешний сервис структуры | Страницы, порядок, композиция, ссылки на блоки |

`ContentService` — предлагаемое имя доменного сервиса для блоков и assets. Операции блоков соответствуют ответственности `BlockService` из исходного документа; окончательное разделение интерфейсов нужно закрепить на первом этапе.

HTML Provider не хранит дерево сайта, не определяет вложенность блоков и не собирает граф из HTML.

Связь `site + creator → connection` хранится явно. Создатель подключения, автор файла и текущий исполнитель запроса — отдельные понятия.

## 2. Этап 1. Зафиксировать контракты

Согласовать:

1. Сущности сайта, подключения создателя, блока и asset.
2. Владение ресурсом и авторство.
3. Канонические адреса и стабильные идентичности ресурсов.
4. Операции создания и изменения контента.
5. Формат ссылки, которую хранит внешний сервис дерева.
6. Разделение исходника и пользовательского представления.
7. Политику удаления ресурсов, на которые могут ссылаться страницы.

Результат: согласованный контракт сущностей, адресов и ответственности. Реализация дерева сайта в HTML Provider не входит в этот контракт.

## 3. Этап 2. Подготовить VFSv2 и ACL для нескольких участников

Это обязательная зависимость. Текущие ограничения scope и разрешающая заглушка ACL не обеспечивают целевую модель доступа.

Необходимые изменения:

- Разрешать вход в scope сайта участникам по ACL, а не только владельцу.
- Отделить доступ к содержимому scope от права управлять scope. Сейчас ядро проверяет одновременно `r` и `w` при входе.
- Определить работу пользовательского, гостевого и сервисного субъектов. Текущий резолвер scope принимает только пользователей.
- Добавить разрешение стабильной идентичности до проверки ACL. Текущий `ResourceRef` содержит адрес по пути.
- Включить в идентичность scope, connection, provider, ID объекта и его представление: `source`, `view`, `metadata`.
- Определить права для create, delete, move, `Stat` и `ReadDir`.
- Обеспечить отказ при ошибке ACL или резолвера.
- Определить политику записи через открытый дескриптор после отзыва прав.

Для первой версии предлагается перепроверять право перед подтверждением отложенной записи. Гарантии относительно одновременного отзыва прав нужно закрепить в общем контракте VFS; сама близость проверки к commit не обеспечивает атомарность.

Результат: два участника работают в одном scope, доступ к подключениям и файлам проверяется независимо, одинаковые ID в разных сайтах не смешиваются.

## 4. Этап 3. Реализовать создание scope и подключений

### Создание сайта

1. Создать запись сайта.
2. Создать связанный scope.
3. Назначить владельца и начальные права.
4. Сохранить связь сайта со scope.

### Добавление создателя

1. Проверить право управления участниками сайта.
2. Создать HTML-подключение в scope сайта.
3. Сохранить связь подключения с создателем.
4. Назначить права на загрузку и изменение контента.

Создание должно быть повторяемым без дублирования. При частичном сбое подключение остаётся неготовым до завершения настройки.

В текущем `ProviderConnection` нет поля владельца. Имя подключения само по себе не задаёт права или связь с создателем.

Если будет выбран backend через `local`, необходимо учитывать: два подключения с одним local account открывают одно дерево. Для независимых пространств в текущей реализации нужны отдельные accounts. При собственном HTML Store изоляция обеспечивается привязкой записей к подключению и проверяется на каждом запросе.

Результат: готовое подключение, в которое можно загружать контент через VFS.

## 5. Этап 4. Реализовать хранение контента и HTML Provider

Предлагаемый адрес блока:

```text
html@creator-17[site-42]:///blocks/<block-id>/
└── meta.json
```

`content.md` является единственным источником контента и может содержать
inline HTML-фрагменты. Отдельный `content.html` не создаётся. Физическая
привязка блока в `meta.json` указывает на каталог с теми же тремя обязательными
файлами. HTML Provider не создаёт их виртуальные копии: клиент обращается к
physical URI через VFS Core.

Для изображений, CSS и других файлов:

```text
html@creator-17[site-42]:///assets/<asset-id>/<filename>
```

Для первой версии предлагаются технические пути со стабильными ID. Отображаемое имя изменяется через метаданные. Если в адрес asset включено имя файла, оно считается неизменяемой технической частью адреса; последующее добавление rename требует сохранения идентичности.

### Хранение

- HTML metadata блоков — SQLite; байты content/CSS/JavaScript принадлежат
  файловому provider.
- Бинарные assets — через интерфейс хранения артефактов/CAS.
- Общие поля: ID, принадлежность подключению, автор, владелец, тип, версия, время изменения.
- Владелец задаётся сервером при создании и не меняется обычной записью `meta.json`.
- Обновление содержимого не меняет автора, владельца или ID.

Доступ к собственному Store после авторизации операции — нормальная работа доменного сервиса. Если источник находится в другом защищённом VFS-ресурсе, обращение идёт через `BoundVFS`.

Публичные HTTP/WebDAV handlers не вызывают HTML Store или доменные сервисы в обход VFS.

Результат: CRUD блоков и assets через провайдер с устойчивой идентичностью.

## 6. Этап 5. Реализовать полный цикл загрузки

Для блоков предлагается двухшаговый сценарий:

1. Клиент создаёт physical bundle с `content.md`, `style.css` и `script.js`.
2. Создание Block metadata сохраняет проверенный `bundleRootUri`.

Для assets используется обычное создание файла. Интерфейс клиента может объединять действия в одну пользовательскую операцию. Пустой блок после сбоя второго шага остаётся определённым состоянием, которое допускает повтор загрузки или удаление.

### Текущие HTTP-операции VFS

| Действие | Запрос |
| --- | --- |
| Создать каталог блока | `POST /api/v2/vfs/directory?uri=<URI>` |
| Загрузить новый файл | `POST /api/v2/vfs/file?uri=<URI>` |
| Заменить содержимое файла | `PUT /api/v2/vfs/file?uri=<URI>` |
| Получить содержимое | `GET /api/v2/vfs/read?uri=<URI>` |
| Получить список | `GET /api/v2/vfs/list?uri=<URI каталога>` |

URI передаётся с URL-кодированием, содержимое файла — в теле запроса. Для
изменения `content.md`, `style.css`, `script.js` используется physical URI,
полученный из `bundleRootUri`; HTML Provider в файловой операции не участвует.

### Обязательные свойства

- Запись сначала поступает во временное хранилище.
- Валидация выполняется до публикации изменения.
- Ошибка передачи отменяет запись.
- Создание с существующим ID возвращает конфликт, включая конкурентное создание.
- Изменение проверяет ожидаемую версию, чтобы один редактор не затёр работу другого.
- Устанавливаются ограничения размера и допустимых типов.
- После успешного сохранения клиент получает ссылку на ресурс и его версию.

Проверку версии нужно согласованно провести через HTTP, WebDAV и контракт записи VFS: текущего общего механизма условной записи недостаточно. Получение ссылки и версии потребует определить ответ операции либо отдельное чтение метаданных, поскольку нынешняя HTTP-замена возвращает `204`.

Результат: загрузка, повторная загрузка и конкурентное редактирование имеют определённое поведение.

## 7. Этап 6. Реализовать получение контента и разделение view/source

Чтение исходника:

```text
Client → VFS → ACL(source) → HTML Provider → ContentService
```

Получение представления:

```text
Client → VFS → ACL(view) → HTML Provider → RenderService
                                         ↓
                              BoundVFS(renderer)
                                         ↓
                                   ACL(source)
```

Текущий `BoundVFS` привязан к actor запроса. Создание доступа от имени renderer должно выполняться доверенной инфраструктурой, без возможности выбрать service principal из клиентских параметров.

До реализации renderer нужно определить, что преобразуется из source в view. Если исходный HTML отдаётся без изменений, разделение URL не скрывает его содержимое. Закрытыми могут оставаться редакторские данные и инструкции, которые не попадают в результат. HTML, отправленный браузеру, доступен получателю.

### Первая версия

- Renderer обрабатывает только запрошенный блок.
- Не загружает произвольные внешние URL и не выполняет серверный JavaScript.
- Другие блоки клиент запрашивает отдельно со своими правами.
- Renderer получает минимальные права чтения необходимых исходников, без write/admin.
- Защищённые ответы не попадают в общий кеш.
- Для выполнения загруженного HTML в браузере определяется изоляция от интерфейса редактора и его учётных данных.
- Определяется способ выдачи MIME-типов и HTTP-заголовков. Нынешний VFS HTTP read возвращает `application/octet-stream`; браузерная выдача HTML и assets требует отдельного транспортного контракта с сохранением входа через VFS.

Результат: пользователь получает разрешённое представление без доступа к редакторскому исходнику или соседним блокам.

## 8. Этап 7. Подключить внешний сервис дерева

Согласовать формат ссылки, которую хранит дерево:

```text
scope + connection + provider + resource ID + representation
```

Сервис дерева:

- хранит композицию страницы;
- возвращает ссылки клиенту;
- не копирует исходники блоков;
- не выдаёт доступ к блоку самим фактом включения в страницу.

HTML Provider отвечает за существование и доступность своего ресурса. Внешний сервис определяет поведение при удалённой ссылке.

На первом этапе предлагается разрешать удаление контента и возвращать `not_found` при последующем обращении к отсутствующему ресурсу, с соблюдением общей политики сокрытия запрещённых ресурсов. Запрет удаления используемых блоков возможен только после появления явного механизма учёта ссылок.

Результат: страница использует контент нескольких создателей, а её дерево остаётся независимым от файлового хранения.

## 9. Этап 8. Интеграционные проверки и ввод в эксплуатацию

Минимальные сценарии приёмки:

1. Создатель A загружает блок; создатель B читает или изменяет его только при соответствующем разрешении.
2. Подмена scope, connection или ID не открывает чужой контент.
3. `view` разрешён, `source` запрещён — исходник недоступен по всем протоколам.
4. `Stat` и `ReadDir` соблюдают выбранную политику видимости.
5. Ошибка передачи не публикует частичный файл.
6. Конкурентное создание не заменяет существующий ресурс.
7. Конкурентное обновление возвращает конфликт.
8. Отзыв доступа действует согласно принятой политике дескрипторов.
9. HTTP и WebDAV дают одинаковые решения ACL.
10. Renderer не может читать произвольный ресурс по входному параметру.
11. Изменение метаданных не позволяет назначить себе владельца.
12. Изменение имени не меняет стабильный ACL; старый адрес не становится обходом.
13. Канонизация, encoded traversal и повторное декодирование не позволяют проверить один ресурс, а открыть другой.
14. Ошибка ACL, резолвера или неизвестное действие не разрешают доступ.
15. Защищённый результат одного пользователя не выдаётся другому через кеш.
16. Логи и ошибки не содержат исходники, токены и секреты подключений.
17. Производственная сборка использует реальный авторизатор и не предоставляет обходных endpoints.

Для проверки провайдера использовать существующий VFS SDK и тестовый harness с запрещающим/настраиваемым Authorizer, а не только разрешающей конфигурацией по умолчанию.

## 10. Порядок работ и первый законченный результат

```text
Контракты
  ↓
VFS/ACL
  ↓
Создание сайта и подключений
  ↓
Хранение и загрузка
  ↓
Чтение и renderer
  ↓
Интеграция дерева
  ↓
Проверка всей цепочки
```

Первый законченный результат — сайт с двумя подключениями создателей, загрузкой блоков и assets, отдельными правами чтения и записи и получением контента по стабильным ссылкам.

В первую версию не входят: серверное построение дерева блоков, извлечение зависимостей из HTML, collaborative editing, история версий с восстановлением, draft/live публикация, CDN, поиск, экспорт, произвольные внешние include и выполнение серверного кода. Версия для защиты от конкурентной записи входит в первую версию и не означает наличие истории редакций.

## 11. Основные точки реализации в репозитории

- `internal/vfs/v2/scope.go` — разрешение scope.
- `internal/vfs/v2/connection.go` — разрешение подключений.
- `internal/common/resource_ref.go` — идентичность ресурса.
- `internal/vfs/v2/core.go` — маршрутизация и проверки доступа.
- `internal/vfs/v2/access.go` — контракт авторизации и текущая заглушка.
- `internal/vfs/v2/bound_fs.go` — внутренние обращения от имени actor.
- `internal/vfs/v2/adapters/httpapi/` — загрузка и чтение через HTTP.
- `internal/vfs/v2/adapters/webdav/` — WebDAV и завершение передачи.
- `internal/vfs/v2/providers/html/` — предлагаемый новый HTML Provider.
- `internal/html/` — предлагаемые доменные сервисы и HTML Store.
- `docs/VFS_V2_IMPLEMENTATION_RU.md` — описание текущей реализации VFSv2.
- `docs/VFS_V2_PROVIDER_SDK_RU.md` — руководство по SDK провайдеров.
