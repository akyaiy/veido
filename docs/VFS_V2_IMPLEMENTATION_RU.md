# VFSv2: фактическое устройство и поведение

> Статус: описание реализации в репозитории на 15 сентября 2026 года, исходная ревизия `948896d0`. Поведение сверено с кодом. Архитектурные пожелания из прежних обзоров не считаются реализованными возможностями.

## 1. Назначение и текущее состояние

VFSv2 — слой Go-приложения, через который разные источники данных доступны как файлы, каталоги и команды. Клиент передаёт исполнителя, адрес ресурса и операцию. Ядро выбирает область ресурсов и подключение, вызывает проверки доступа и передаёт работу соответствующему провайдеру.

Одинаковый интерфейс подходит для обычных файлов и для виртуальных документов. Например, чтение файла у `local` возвращает содержимое из хранилища, а чтение `config.json` у `scopes` формирует представление записи в БД. Источник данных определяет провайдер.

В репозитории существуют ядро VFSv2, SQLite-резолверы, пул провайдеров, провайдеры `local`, `scopes`, `debug`, HTTP- и WebDAV-адаптеры, браузерный клиент и SDK. Отдельная команда `cmd/vfsv2webdav` собирает VFSv2 и предоставляет оба протокола. Основное приложение в `internal/app/server.go` пока собирает прежнюю VFS из `internal/vfs`; наличие VFSv2 в репозитории не означает переключение основного сервера на неё.

**Авторизация подключаемая, но ACLv2 пока не реализован.** Ядро вызывает `Authorizer.Can`, однако имеющийся `ACLAuthorizer` всегда возвращает `true`. Сборки `cmd/vfsv2webdav` и `cmd/vfsv2debug` используют собственный `allowAllAuthorizer`; стандартный lifecycle sink только пишет отладочные сообщения. Ограничения резолверов и провайдеров при этом продолжают действовать.

Этот файл объясняет текущую систему целиком. Целевая модель правил доступа описана отдельно в [концепции ACLv2](ACL_V2_CONCEPT_RU.md).

## 2. Основные понятия

| Понятие | Значение в текущем коде |
| --- | --- |
| Actor, исполнитель | `Actor{Kind, ID}`: кто выполняет операцию. Например, `user:42` |
| Scope, область ресурсов | Именованная область с ключом, видом и владельцем. Содержит подключения провайдеров |
| Provider, провайдер | Реализация файловых операций для определённого источника данных |
| Connection, подключение | Настроенный экземпляр источника внутри scope: тип провайдера, ключ, конфигурация, состояние |
| CanonURI | Проверенная строка адреса: провайдер, подключение, необязательный scope, абсолютный путь |
| ResourceAddress | Разобранные поля исходного адреса |
| ResourceRef | Ссылка, передаваемая авторизатору и lifecycle sink после выбора scope и connection |
| Node | Метаданные элемента: имя, вид, признак каталога, размер, время обновления |
| File | Открытый дескриптор с `Read`, `Write`, `Seek`, `Close`, `Stat` |
| BoundVFS | Доступ к ядру, привязанный к actor текущего запроса |

Исполнитель и область независимы: `user:42` остаётся исполнителем даже при явно указанном другом scope. Подключение также не является пользователем. Например, `local` аутентифицирует свой account из конфигурации connection, а actor берёт из контекста запроса.

## 3. Адресация: что реально принимает ядро

Пример полного адреса:

```text
local@default[alice]:///docs/report.md
│     │       │        └ путь /docs/report.md внутри провайдера
│     │       └ точный ключ scope: alice
│     └ точный ключ connection: default
└ ключ провайдера: local
```

Текущий парсер требует непустые provider и connection. Scope можно опустить или оставить пустым:

```text
local@default[alice]:///docs/report.md
local@default:///docs/report.md
local@default[]:///docs/report.md
```

Последние два адреса требуют поиска scope по умолчанию для actor. Имя `default` не подставляется автоматически: `local:///docs/report.md` текущему формату не соответствует.

Путь должен уже быть абсолютным и очищенным по правилам `path.Clean`. Повторные слеши, сегменты `.` и `..`, завершающий слеш у некорневого пути отклоняются при `CastURI`. Корень записывается как `:///`.

Строка в квадратных скобках — ключ БД. Записи `[user:17]` или `[scope:1]` не имеют специального механизма преобразования в пользовательскую область. Отдельного поля для query-параметров ресурса нет: часть после `://` разбирается как путь. Описанный в ранних обзорах `?export=pdf` не является реализованным модификатором чтения.

Ядро принимает канонические URI. Преобразование удобного пути WebDAV в такой URI выполняет адаптер; общего mount-router для произвольных путей в `VFSCore` нет.

### Текущий ResourceRef

```go
type ResourceRef struct {
    ProviderKey   string
    ConnectionKey string
    ScopeKey      string
    Path          string
}
```

Ядро подставляет разрешённые scope и connection, но сохраняет идентичность по пути. Оно не запрашивает у провайдера стабильный ID файла или цепочку его родителей. Даже если `local` внутри использует `metadata.id`, этот ID не попадает в текущую проверку ACL.

## 4. Как проходит запрос

Для примера возьмём чтение существующего файла:

```text
actor = user:42
URI   = local@default[alice]:///docs/report.md
```

Порядок в `VFSCore.OpenFile(..., O_RDONLY)`:

1. Разобрать URI в `ResourceAddress`.
2. Найти scope `alice` через `ScopeResolver`.
3. Вызвать `Can(actor, r, scopeRef)`, затем `Can(actor, w, scopeRef)`.
4. Найти активное и готовое подключение `local@default` в `alice`.
5. Составить `ResourceRef{local, default, alice, /docs/report.md}`.
6. Вызвать `Can(actor, r, resourceRef)`.
7. Получить или создать экземпляр провайдера из пула.
8. Положить в контекст `RequestContext` и `BoundVFS` текущего actor.
9. Вызвать `provider.OpenFile(ctx, "/docs/report.md", O_RDONLY)`.
10. Вернуть дескриптор; клиент или адаптер читает поток и закрывает его.

Проверки относятся к конкретным точкам вызова `Can`. Реальный запрет зависит от переданного авторизатора. Проверка через разрешающую заглушку не превращается в применение ACL-правил.

### Особенность проверки scope

Сейчас ядро строит для входа в область следующую ссылку:

```text
ProviderKey   = scopes
ConnectionKey = scopes
ScopeKey      = system
Path          = /alice
```

Это проверка `r` **и** `w`, даже при чтении файла. При этом фактический каталог области у провайдера `scopes` имеет путь `/scopes/alice`. Ссылка проверки входа и каталог управления областью сейчас различаются. Для настоящего ACL необходимо согласовать их идентичность и политику входа.

## 5. Кто за что отвечает

| Компонент | Ответственность |
| --- | --- |
| `VFSFrontend` | Контракт операций с actor и каноническими URI |
| `VFSCore` | Разрешение адреса, вызовы авторизации, выбор провайдера, контекст, события создания/перемещения/удаления |
| `ScopeResolver` | Поиск явной области либо области по умолчанию |
| `ConnectionResolver` | Поиск connection по scope/provider/key и проверка состояния подключения |
| `ProviderRegistry` / SDK catalog | Соответствие ключа провайдера его фабрике; catalog также хранит описание провайдера |
| `CachedProviderPool` | Создание и переиспользование провайдеров для connection |
| `Authorizer` | Ответ на `Can(actor, action, ref)` |
| `ResourceLifecycleSink` | Уведомления после изменений ресурсов |
| `FSProvider` | Файловые операции, доменная валидация, работа со своим хранилищем |
| HTTP / WebDAV | Преобразование протокола в вызовы ядра и обратно |

У `FSProvider` нет actor в сигнатуре каждого метода: сведения о запросе доступны из контекста. Ядро также разбивает путь для `Mkdir` на родителя и имя, а для `Move` — на источник, нового родителя и новое имя.

### Переиспользование экземпляров

Пул кеширует провайдер по тройке `ScopeKey / ProviderKey / ConnectionKey`. Если меняется `ConfigVersion`, старый экземпляр удаляется из кеша и закрывается, если реализует `io.Closer`; затем вызывается фабрика нового. Есть явный `Invalidate`.

Один экземпляр обслуживает запросы разных actor. Провайдер должен держать actor и request context в данных конкретного вызова, а свои общие изменяемые данные синхронизировать.

### Вложенные обращения

Провайдер получает `BoundVFS` из контекста и использует его для обращения к другим VFS-ресурсам. Так повторно выполняются маршрутизация, проверки и события с тем же actor. `SelfURI(path)` помогает построить адрес внутри собственного подключения.

Прямой вызов CRUD другого провайдера в обход ядра нарушает этот контракт. SDK-композиция поддеревьев допустима внутри одного connection и не заменяет обращение к другому connection через `BoundVFS`.

## 6. Какие проверки вызывает ядро сегодня

Перед каждой операцией выполняется описанная выше проверка scope: `r` и `w`. Для `Move` разрешаются обе стороны. Затем действуют следующие проверки:

| Операция | Дополнительные вызовы `Can` |
| --- | --- |
| `Stat` | `r` на целевой путь |
| `ReadDir` | `r` на каталог |
| `OpenFile(O_RDONLY)` | `r` на файл |
| `OpenFile` с записью, append или truncate | `w` на файл; при режиме чтения также `r` |
| `OpenFile` с `O_CREATE` | Дополнительно `w` на родителя, даже если файл уже существует |
| `Mkdir` | `w` на родителя создаваемого каталога |
| `Move` | `w` на источник, его родителя и нового родителя |
| `Delete` | `w` на удаляемый ресурс |
| `Control` | `x` на целевой ресурс |

`O_RDWR` требует и чтение, и запись. Создание через `O_CREATE | O_WRONLY` требует `w` как на целевой путь, так и на родителя, хотя целевого файла ещё может не существовать.

Ядро не выполняет отдельный проход с `x` по предкам и не фильтрует каждый элемент результата `ReadDir` через `Can`. Оно также не интерпретирует имя команды `Control`: несколько команд одного URI проходят одну проверку `x` на этот URI.

Перемещение возможно только внутри одного scope/provider/connection. Иное сочетание возвращает unsupported до вызова провайдера; универсального копирования между подключениями нет.

## 7. Области и подключения в SQLite

Метаданные маршрутизации находятся в трёх таблицах:

| Таблица | Что хранит |
| --- | --- |
| `vfs_scopes` | `scope_key`, `kind`, `owner_subject_key`, даты |
| `vfs_principal_default_scopes` | Соответствие `(principal_type, principal_id)` → `scope_key` |
| `vfs_provider_connections` | ID, scope, provider, connection key, display name, JSON-конфигурацию, её версию, status, ready |

SQLite `ScopeResolver` сейчас принимает только `ActorUser` с непустым ID. Явный scope находится, если он системный либо принадлежит actor. Поиск области по умолчанию использует сохранённое соответствие в БД. Гостевые и сервисные actor объявлены типами, но этот резолвер их отклоняет.

`ScopeStorage.List` возвращает области по `owner_subject_key`. Это ещё не список всех областей, доступных через группы, sharing или рекурсивные ACL. `Get` по ключу не выполняет такую фильтрацию и рассчитан на внешнюю авторизацию вызова.

`ConnectionResolver` требует точный connection key, `status = active` и `ready = true`. Для `scopes@scopes[system]` оставлено исключение по ready для начальной настройки. Изменение конфигурации повышает её версию, которую использует пул.

В схеме ключ connection уникален внутри scope независимо от provider. Для непустого display name также есть уникальность внутри scope. Display name служит для отображения; переименование display name не меняет канонический connection key.

## 8. Реальные провайдеры

### 8.1. `scopes`: управление метаданными VFS через VFS

Системное подключение обычно адресуется `scopes@scopes[system]:///`. Его дерево:

```text
/
├── scopes/
│   └── <scope-key>/
│       ├── info.json
│       └── connections/
│           └── <provider-key>@<connection-key>/
│               ├── info.json
│               ├── profile.json
│               ├── config.json
│               └── status.json
└── me/
    └── default_scope.json
```

`info.json` формируется при чтении. `profile.json` меняет отображаемое имя connection, `config.json` — его JSON-конфигурацию, `status.json` — status/ready, `me/default_scope.json` — область по умолчанию текущего actor.

Создание каталога под `/scopes` создаёт пользовательский scope. К введённому имени добавляется префикс из первых шести hex-символов SHA-256 ключа actor. Создание каталога `<provider>@<display-name>` под `connections` создаёт connection со сгенерированным ключом, пустой конфигурацией, `active` и `ready=false`.

Провайдер допускает удаление обычных scope и connection; удаление системного scope запрещает отдельный обработчик. Перемещение connection внутри своего родителя меняет display name. Дерево построено через SDK `Collection`, `JSON`, `Document`.

Листинг scope ограничен владельцем, но прямой `Lookup` получает scope по ключу. Поэтому список видимых элементов не заменяет авторизацию прямых обращений к системному провайдеру.

### 8.2. `local`: account, дерево метаданных и содержимое по хешу

У `local` два режима подключения:

- `bootstrap`: виртуальные документы для создания local account. Запись `create_request.json` с `done=true` создаёт account. Полученные subject key и secret затем используются в конфигурации connection.
- `account`: фабрика проверяет `subject_key` и `secret`, получает корневой узел account и открывает его файловое дерево.

Дерево хранится в `metadata`, сведения о содержимом — в `artifacts`, а байты — в content-addressed storage, то есть хранилище с адресацией по хешу содержимого. По умолчанию используется `./data/cas`; путь можно задать конфигурацией. Account связан с `RootNodeID`, относительно которого провайдер разрешает пути.

`local` реализует чтение, создание, замену и append файлов, каталоги, перемещение и удаление. При замене содержимого сохраняется числовой ID существующего узла, но текущий VFS `ResourceRef` этого ID не использует. Произвольная запись с перемещением позиции не поддерживается; append копирует прежнее содержимое в новый поток перед добавлением данных. `Control` файлового backend возвращает unsupported.

При сохранении файла `metadata.owner` берётся из actor текущего запроса; при отсутствии actor используется владелец account или его subject key. Поэтому запись другим actor может изменить owner существующего файла. Замена узла внутри SQL-транзакции выполнена через удаление и вставку с тем же ID. Это важно учитывать при добавлении правил владельца и внешних ключей ACL.

Служебное поддерево `/%account%` подключено через SDK-композицию и скрыто из обычного листинга. Скрытие влияет на отображение, а не на права прямого доступа.

### 8.3. `debug` и расширения

`debug` — диагностический провайдер для проверки вызовов и контекста. Внешние провайдеры и проекции `users`, `functions`, `html`, `shared` из архитектурных сценариев не зарегистрированы как реализации VFSv2 в текущей сборке `cmd/vfsv2webdav`. Старые провайдеры из `internal/vfs/providers` относятся к предыдущей VFS.

## 9. Запись, подтверждение и события

`File` предоставляет файловый интерфейс, но не обещает поддержку каждого режима. Наличие метода `Seek` не гарантирует возможность произвольного позиционирования для записи.

Для отложенного сохранения предусмотрен дополнительный интерфейс `WriteFile` с `Commit` и `Abort`. У таких файлов `Close` означает `Commit` для совместимости с файловыми клиентами. Правильное завершение передачи:

```go
file, err := frontend.OpenFile(ctx, actor, uri, flags)
if err != nil {
    return err
}
_, transferErr := io.Copy(file, source)
return vfs.FinishWrite(file, transferErr)
```

`FinishWrite` подтверждает полную передачу либо отменяет staged-запись при ошибке источника. Для обычного файла он вызывает `Close`; автоматического отката прямой записи не предоставляет.

У `local` запись сначала идёт во временный объект. Подтверждение публикует содержимое по хешу, регистрирует artifact и обновляет ссылку узла metadata. Это несколько шагов, а не общая транзакция файловой системы, БД и ACL.

События ядра:

| Изменение | Когда вызывается lifecycle sink |
| --- | --- |
| Новый staged-файл | После успешного commit |
| Новый файл с прямой записью | После успешного `OpenFile` |
| Каталог | После успешного `provider.Mkdir` |
| Перемещение | После успешного `provider.Move` |
| Удаление | После успешного `provider.Delete` |

Ошибка sink не откатывает уже сохранённое изменение. Для нового staged-файла уведомление не повторяется при повторном `Close`. Произвольная доменная команда `Control` сама по себе не создаёт события файлового lifecycle.

Проверка существования перед `OpenFile` используется для обнаружения создания, но не обеспечивает атомарность `O_EXCL`. В текущем `local` проверка `O_EXCL` происходит при открытии, а commit заново ищет узел по имени и может заменить появившийся узел. Гарантию создания строго нового файла при конкуренции нельзя выводить только из флагов HTTP-адаптера.

## 10. HTTP, WebDAV и браузерный клиент

### HTTP API

В `cmd/vfsv2webdav` и `providerdev` адаптер смонтирован на `/api/v2/vfs`. URI передаётся URL-encoded в параметре `uri`; actor получает внедрённая функция `ActorResolver`.

| HTTP-маршрут относительно prefix | Операция | Успех |
| --- | --- | --- |
| `GET /stat` | Метаданные | `200`, JSON Node |
| `GET /list` | Каталог | `200`, `{ "items": [...] }` |
| `GET /read` | Чтение | `200`, поток байтов |
| `POST /file` | Создание, `O_CREATE | O_WRONLY | O_EXCL` | `201` |
| `PUT /file` | Замена, `O_WRONLY | O_TRUNC` | `204` |
| `POST /directory` | Каталог | `201`, JSON Node |
| `POST /move` | Цель в JSON `target_uri` | `204` |
| `DELETE /resource` | Удаление | `204` |
| `POST /control` | Команда из query `command`, тело — байты | `200`, байты |

Адаптер проверяет входные параметры, вызывает ядро, завершает запись через `FinishWrite` и преобразует ошибки. Он не реализует собственный ACL и не интерпретирует тело provider-команды. Лимиты по умолчанию: запись файла — 32 MiB, `Control` — 1 MiB, JSON-запрос перемещения — 64 KiB.

Ошибки имеют оболочку `error` с `code`, `message` и необязательными `operation`, `request_id`. Примеры: `400 invalid_argument`, `403 permission_denied`, `404 not_found`, `409 already_exists`, `501 unsupported`. HTTP-чтение возвращает `application/octet-stream`; Range, ETag, пагинация каталога, batch и частичная запись через PATCH не реализованы этим адаптером.

В `cmd/vfsv2webdav` actor устанавливает Basic Auth middleware. HTTP-адаптер сам не проверяет JWT: другой механизм аутентификации должен установить actor через свою интеграцию. Команда также создаёт/сбрасывает тестового `admin` с паролем `admin` и использует разрешающий авторизатор; это существенная характеристика данной сборки, а не пример готовой production-конфигурации.

### WebDAV

Есть два режима:

1. Один базовый URI: путь WebDAV дополняет путь внутри выбранного connection.
2. Обзор областей: корень содержит `Home` и области из `scopes`; внутри области показываются подключения по display name, далее идёт дерево провайдера.

`Home` разрешается в scope по умолчанию. Системная область отображается как `.system`. В списке подключений адаптер проверяет active/ready и возможность выполнить `Stat` корня провайдера. Это навигационное представление поверх вызовов VFS, а не отдельная система идентичности ресурсов.

Обёртка `TransactionalWrites` обеспечивает отмену staged-загрузки при ошибке HTTP-тела, поскольку стандартный WebDAV handler может вызвать `Close` после неудачной передачи. Она уже подключена в `cmd/vfsv2webdav` и `providerdev`.

### JavaScript

`data/HTML/frontend/js/vfsv2.js` предоставляет `VFSv2.read`, `create`, `write`, `stat`, `readdir`, `mkdir`, `move`, `remove`, `control` и методы для JSON/байтов. Библиотеку нужно подключить на страницу. Она передаёт настроенные заголовки аутентификации; поддержка конкретного способа входа определяется сервером.

## 11. Как добавить провайдер

Публичные пакеты используют module path `MyServer`:

| Пакет | Назначение |
| --- | --- |
| `pkg/vfs` | Контракты VFS, actor, URI, ошибки и файловые дескрипторы |
| `pkg/vfs/providersdk` | Деревья, коллекции, документы, команды, backend-адаптеры, композиция, фабрики |
| `pkg/vfs/providertest` | Настоящее ядро с тестовыми резолверами и проверкой дерева |
| `pkg/vfs/providerdev` | HTTP/WebDAV-сервер и инспектор для разработки |
| `pkg/vfs/adapters/webdav` | Публичный WebDAV-адаптер и обёртка загрузок |

Для виртуальной сущности SDK предлагает `Directory`, `Collection`, `JSON`, `Document`, `Command`; для существующей ФС — `FromBackend`, read-only `FromFS` либо непосредственную реализацию `FSProvider`. `virtfs` — нижележащий помощник для синтетических деревьев.

SDK `Build` проверяет объявления и замораживает структуру. `Collection.Lookup` проверяет существование сущности и переиспользует загруженное значение только внутри операции. `Document` валидирует полную замену данных перед сохранением. `Command` вызывается через `Control` и требует `x` на его ресурсе; отдельный файл действия автоматически не создаётся.

Генератор `cmd/vfsprovider` создаёт пример провайдера, тест и запуск. Тестовое окружение по умолчанию разрешает все запросы; для проверки отказов нужно передать свой `Authorizer`. Подробнее: [руководство SDK](VFS_V2_PROVIDER_SDK_RU.md).

## 12. Граница с концепцией ACLv2

Чтобы читать этот файл без прежних обсуждений, полезно свести главные различия в одну таблицу:

| Сейчас в коде VFSv2 | Что ещё относится к концепции ACLv2 |
| --- | --- |
| Вызовы `Can`, разрешающая реализация | Хранилище allow/deny, группы, наследование, owner fallback |
| `ResourceRef` содержит путь | Стабильная идентичность и получение предков у провайдера |
| Scope ограничивается резолвером по user/system/owner | Доступ к чужим и общим областям по ACL |
| Вход в scope требует `r` и `w` | Разделение видимости, входа и управления через `r/w/x` |
| Проверки методов приведены в разделе 6 | Проверка прохода по предкам и окончательная семантика create/delete/move |
| Lifecycle sink вызывается после изменений и обычно ничего не сохраняет | Согласование правил с созданием, удалением и перемещением ресурсов |
| Реальные `local`, `scopes`, `debug` | Sharing и доменные/внешние провайдеры из сквозных сценариев |

VFSv2 уже выполняет маршрутизацию, файловые операции и адаптацию протоколов. Полная ресурсная авторизация должна быть реализована и встроена с учётом этих различий; одной замены `return true` недостаточно.
