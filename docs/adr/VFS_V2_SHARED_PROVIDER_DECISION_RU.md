# ADR-004: Shared-провайдер и пользовательский sharing

> Статус: принятое целевое архитектурное решение, не описание готовой реализации.  
> Дата решения: 19 сентября 2026 года.  
> Уточнено 20 сентября 2026 года: междоменное управление ACL и проверка subject идут через VFS; общая SQL-транзакция между Shared и ACL запрещена.  
> Реализация ACLv2 и точный контракт управления ACL будут спроектированы отдельно.  
> Связанные документы: [концепция ACLv2](../ACL_V2_CONCEPT_RU.md), [ACL lifecycle](ACL_LIFECYCLE_ARCHITECTURE_RU.md), [scope resolution](VFS_V2_SCOPE_RESOLUTION_DECISION_RU.md), [текущая реализация VFSv2](../VFS_V2_IMPLEMENTATION_RU.md).

## 1. Контекст и цель

Пользователь должен иметь возможность поделиться файлом или каталогом из любого
VFS-провайдера и увидеть доступные ему ресурсы в отдельном дереве `shared`.

Исходные провайдеры `local`, `gdrive`, `s3` и другие не должны реализовывать
собственную семантику sharing. Они отвечают только за свои ресурсы. Sharing
реализуется отдельным заменяемым провайдером-проекцией.

`shared` не хранит содержимое файлов. Он хранит связь между удобным виртуальным
путём и каноническим URI исходного ресурса, а операции над содержимым повторно
направляет через VFS Core.

Пример виртуальной ссылки:

```text
shared@me[bob]:///incoming/alice/demo
```

Она может указывать на исходный ресурс:

```text
local@default[alice]:///projects/demo
```

## 2. Принятое решение

Принята следующая модель:

```text
Что отображается в shared = таблица vfs_shared_links
Что actor может сделать   = ACL
Кто выполняет операцию    = VFS Core
Где лежат данные          = исходный provider
Идентичность ресурса      = канонический VFS URI
```

Таблица ссылок и ACL решают разные задачи:

- `vfs_shared_links` является источником истины о наличии и представлении ссылки;
- ACL является единственным источником внутреннего решения о разрешении; provider или его backend
  могут дополнительно отказать, но не могут разрешить операцию после ACL `deny`;
- строка таблицы сама по себе не предоставляет права;
- ACL-право само по себе не создаёт элемент в дереве `shared`.

Sharing является пользовательским сценарием управления обычными правами, но не
становится отдельным ACL action или видом ACL-правила.

## 3. Архитектурные границы

| Компонент | Ответственность |
| --- | --- |
| Auth | Устанавливает доверенного `actor` |
| ACL | Проверяет и изменяет права относительно канонического URI |
| VFS Core | Разрешает URI, применяет ACL и маршрутизирует операции |
| Shared Provider | Хранит и отображает виртуальные ссылки |
| Исходный provider | Выполняет разрешённую операцию над реальным ресурсом |

Shared Provider не должен:

- разрешать операцию в обход ACL;
- обращаться к backend другого провайдера напрямую;
- получать прямой ACL management service, Auth service или доступ к их таблицам;
- добавлять в ACL тип правила `share` или provider-specific признаки;
- использовать provider-local ID исходного ресурса как системную идентичность;
- требовать поддержки sharing от исходного провайдера;
- изменять семантику Auth, ACL или VFS Core.

Удаление регистрации `shared` убирает только виртуальное дерево и интерфейс
управления ссылками. Прямой доступ по URI и работа Auth, ACL и VFS Core не должны
измениться.

## 4. Отклонённые варианты

### 4.1. Строить shared только по ACL

Этот вариант отклонён. Если перечислять все ресурсы, доступные actor через ACL,
в `shared` попадут собственные ресурсы, системные права, наследуемые правила и
другие элементы, которые пользователь явно не расшаривал.

Кроме лишнего содержимого возникает циклическая проблема: виртуальная ссылка
сама является VFS-ресурсом и также проходит обычную авторизацию.

### 4.2. Добавить тип `share` в ACL

Этот вариант отклонён. Универсальная модель ACL не должна зависеть от одного
провайдера или пользовательского сценария. Shared Provider использует обычные
права ACL и собственную таблицу представления.

### 4.3. Реализовать sharing в каждом исходном провайдере

Этот вариант отклонён. Он заставил бы `local`, `gdrive`, `s3` и другие адаптеры
реализовывать одну системную возможность и влиять на общую модель доступа.

### 4.4. Отзывать share через Delete

Удаление элемента из `outgoing` рассматривалось как способ отзыва доступа, но
было отклонено в пользу явной команды `Control("revoke")`. Это проще для UI и не
смешивает удаление виртуальной ссылки с удалением исходного файла или каталога.

## 5. Идентичность ссылки и исходного ресурса

В таблице хранится канонический VFS URI:

```text
local@default[alice]:///projects/demo
```

Глобальный `resource_id` не вводится. Внутренние идентификаторы конкретного
провайдера не входят в контракт shared и не попадают в URI или ACL.

Технический первичный ключ строки таблицы, если он потребуется реализации,
остаётся локальной деталью Shared Provider. Он не становится системной
идентичностью ресурса.

Виртуальный URI также не заменяет исходный URI. Он является только адресом
проекции:

```text
shared URI -> target URI
```

## 6. Хранилище ссылок

Логическая таблица:

```sql
CREATE TABLE vfs_shared_links (
    recipient_user_id   INTEGER NOT NULL,
    recipient_name      TEXT NOT NULL,
    granted_by_user_id  INTEGER NOT NULL,
    granted_by_name     TEXT NOT NULL,
    target_uri          TEXT NOT NULL,
    alias               TEXT NOT NULL,
    access_mode         TEXT NOT NULL,
    status              TEXT NOT NULL,
    acl_grant_uri       TEXT,
    created_at          DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at          DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (recipient_user_id, target_uri),
    UNIQUE (recipient_user_id, granted_by_user_id, alias)
);
```

`acl_grant_uri` — канонический URI созданного ACL-ресурса или набора правил. Он может
отсутствовать, пока ссылка находится в `pending`, но должен быть сохранён до перехода в
`active`. Это не идентификатор target-ресурса, а ссылка на ресурс ACL Provider, нужная для точного
идемпотентного отзыва выданных sharing-операцией прав.

Таблица Shared не содержит foreign key на Auth-таблицу `users` и не читает её напрямую. Идентификаторы
пользователей являются допустимыми глобальными identity-значениями, но их существование и статус
проверяются владеющим Auth/ACL-контуром, а не Shared. Нужные для дерева имена получаются
через VFS-ресурс владеющего домена или хранятся в `recipient_name` и `granted_by_name` как локальная
проекция, обновляемая событиями. Одинаковый alias допустим от разных grantor, так как их ссылки находятся
в разных ветвях `/incoming/<grantor>/`.

`access_mode` хранит выбранный в UI профиль и помогает восстанавливать
рассогласованное состояние. При выполнении защищённой операции эта колонка не
заменяет ACL-проверку.

Допустимые начальные профили:

```text
viewer
editor
```

Их точное преобразование в правила будет определено вместе с ACLv2.

Состояния ссылки:

| Состояние | Значение |
| --- | --- |
| `pending` | Ссылка создаётся и ещё не показывается получателю |
| `active` | Ссылка и требуемые права настроены |
| `revoking` | Ссылка скрыта, выполняется отзыв прав |
| `broken` | Исходный URI удалён или больше не разрешается |

Получателю показываются только активные ссылки, которые проходят актуальную
проверку через VFS Core.

## 7. Виртуальное дерево

Для пользовательского scope создаётся connection:

```text
provider       = shared
connection_key = me
display_name   = Shared
```

Корневое дерево:

```text
shared@me[user-scope]:///
  incoming/
  outgoing/
```

`incoming` содержит ссылки, полученные текущим пользователем:

```text
shared@me[bob]:///
  incoming/
    alice/
      demo/
```

`outgoing` содержит ссылки, созданные текущим пользователем:

```text
shared@me[alice]:///
  outgoing/
    bob/
      demo/
```

`incoming` строится по `recipient_user_id`, а `outgoing` — по
`granted_by_user_id`. Actor всегда берётся из доверенного request context, а не
из входного JSON или виртуального пути.

Alias является частью представления. Он не участвует в решении ACL и может
оставаться прежним после перемещения исходного ресурса.

## 8. Пользовательский flow

Пользователь открывает ресурс в любом VFS-провайдере:

```text
local@default[alice]:///projects/demo
```

В интерфейсе он выбирает действие `Поделиться`, затем указывает:

```text
Получатель: Bob
Режим: Просмотр
Рекурсивно: Да
Имя ссылки: demo
```

UI отправляет команду в `shared`-провайдер Alice. Исходный `local`-провайдер не
получает команду sharing и ничего о ней не знает.

После успешного выполнения Bob видит:

```text
shared@me[bob]:///incoming/alice/demo
```

Alice видит ту же связь в управляющем представлении:

```text
shared@me[alice]:///outgoing/bob/demo
```

## 9. Управляющие операции Control

Все изменения sharing выполняются явными командами `Control` на разделе
`outgoing`:

```text
create
update
revoke
```

Обычный `Delete` не используется для отзыва доступа. Удаление корня ссылки в
`incoming` или `outgoing` должно возвращать `unsupported` либо
`permission_denied`, а не удалять исходный ресурс.

### 9.1. Создание

```text
Control(
    shared@me[alice]:///outgoing,
    "create",
    {
        target_uri: "local@default[alice]:///projects/demo",
        recipient_user_id: 17,
        access: "viewer",
        recursive: true,
        alias: "demo"
    }
)
```

Последовательность:

1. Получить actor из доверенного контекста.
2. Проверить и канонизировать `target_uri`.
3. Проверить существование исходного ресурса через `BoundVFS.Stat`.
4. Сформировать универсальный subject key получателя; Shared не вызывает Auth service напрямую.
5. Создать запись в состоянии `pending`.
6. Через `BoundVFS.Control` вызвать ACL Provider, который проверит subject через свою Auth-интеграцию,
   авторизует изменение политики и создаст обычные ACL-правила.
7. Сохранить вернутый канонический `acl_grant_uri` и перевести запись в `active`.
8. Вернуть виртуальный URI получателя.

Пример ответа:

```json
{
  "target_uri": "local@default[alice]:///projects/demo",
  "virtual_uri": "shared@me[bob]:///incoming/alice/demo",
  "status": "active"
}
```

### 9.2. Изменение режима

```text
Control(
    shared@me[alice]:///outgoing,
    "update",
    {
        target_uri: "local@default[alice]:///projects/demo",
        recipient_user_id: 17,
        access: "editor"
    }
)
```

Shared Provider находит существующую ссылку и вызывает через `BoundVFS.Control`
команду изменения её `acl_grant_uri`. ACL Provider атомарно заменяет только принадлежащий этому
ACL-ресурсу набор обычных правил. Alias и виртуальный путь не меняются.

### 9.3. Отзыв

```text
Control(
    shared@me[alice]:///outgoing,
    "revoke",
    {
        target_uri: "local@default[alice]:///projects/demo",
        recipient_user_id: 17
    }
)
```

Последовательность:

1. Найти ссылку, созданную текущим actor.
2. Перевести её в состояние `revoking`.
3. Сразу скрыть её из `incoming` получателя.
4. Через `BoundVFS.Control` отозвать сохранённый `acl_grant_uri`.
5. После успешного отзыва удалить строку таблицы.

Исходный файл или каталог не удаляется. Групповые, наследуемые и
административные права, полученные другим способом, также не должны удаляться.

## 10. Доступ к содержимому

Для пути:

```text
shared@me[bob]:///incoming/alice/demo/readme.md
```

Shared Provider:

1. Находит ссылку `/incoming/alice/demo`.
2. Получает её `target_uri`.
3. Безопасно присоединяет относительный путь `/readme.md`.
4. Получает конечный канонический URI:

```text
local@default[alice]:///projects/demo/readme.md
```

5. Вызывает операцию через actor-bound VFS.
6. VFS Core применяет актуальную авторизацию.
7. После успешной проверки операция попадает в исходный provider.

Делегирование:

| Shared-операция | Вызов через BoundVFS |
| --- | --- |
| `Stat` | `BoundVFS.Stat` |
| `ReadDir` | `BoundVFS.ReadDir` |
| `OpenFile` | `BoundVFS.OpenFile` |
| `Mkdir` | `BoundVFS.Mkdir` |
| `Delete` вложенного ресурса | `BoundVFS.Delete` |
| `Move` внутри одного исходного дерева | `BoundVFS.Move` |

Удаление точного корня виртуальной ссылки запрещено. Для отзыва используется
`Control("revoke")`.

`Move` между разными shared-ссылками и разными исходными connections в первой
версии не поддерживается.

Раздел `outgoing` является управляющим представлением. Мутации содержимого через
него в первой версии запрещены; владелец изменяет ресурс по исходному URI.

## 11. Граница с ACLv2

Конкретная схема ACL, алгоритм управления правилами и авторизация изменения
политики будут определены отдельно. Shared Provider не должен фиксировать эти
решения внутри своей модели.

Управление ACL не является исключением из междоменной границы: Shared вызывает ресурсы ACL Provider
только через `BoundVFS`. Прямой management-интерфейс ACL в Shared не внедряется. Внутренний read-only вызов
`VFS Core -> Authorizer.Can` остаётся kernel-контрактом и не открывает провайдерам обходной путь.

Для shared обязательны следующие свойства будущего ACL:

- строка `vfs_shared_links` не является разрешением;
- окончательная операция проверяется ACL после разрешения target URI;
- управление правами выполняется через универсальный ACL-контракт;
- ACL не содержит типа правила `share`;
- отзыв удаляет только права, выданные соответствующей операцией, и не затрагивает
  независимые групповые или наследуемые разрешения;
- доступ к виртуальному дереву не должен автоматически открывать соседние
  ресурсы исходного scope.

Для собственной `shared`-проекции пользователю может быть выдано одно базовое
разрешение на корень connection. Отдельное правило на каждый alias не требуется.
Это разрешение даёт доступ к представлению, но не заменяет проверку исходного
URI.

## 12. Lifecycle

Shared хранит URI, поэтому должен участвовать в обработке namespace lifecycle.

### 12.1. Move и rename

При событии:

```text
old URI -> new URI
```

обработчик shared обновляет `vfs_shared_links.target_uri`. Для перемещения
каталога обновляются также ссылки, URI которых находится под старым prefix.

ACL lifecycle независимо сохраняет согласованность прав. Shared lifecycle не
пишет ACL напрямую и не заменяет ACL overlay.

Alias может остаться прежним, поэтому пользовательская ссылка продолжает
выглядеть стабильно после перемещения исходного ресурса.

### 12.2. Delete

При удалении исходного URI связанная ссылка удаляется либо переводится в
`broken`. Она немедленно перестаёт отображаться в `incoming`.

Повторное создание другого ресурса по тому же URI не должно автоматически
восстанавливать старую ссылку. Для этого используется lifecycle generation и
tombstone, описанные в ADR по ACL lifecycle.

### 12.3. Требования

Обработчики shared lifecycle должны быть:

- идемпотентными;
- восстанавливаемыми после частичного сбоя;
- безопасными для prefix move;
- независимыми от provider-local ID;
- подключаемыми как отдельный observer, без зависимости VFS Core от `shared`.

## 13. Согласованность

Shared и ACL не объединяют свои изменения в общую SQL-транзакцию, даже если физически используют одну БД.
Shared Provider не получает транзакционный доступ к ACL-таблицам, а ACL Provider — к `vfs_shared_links`.
Все междоменные изменения идут через VFS-контракты.

Согласованность обеспечивают состояния `pending` и `revoking`, устойчивый idempotency key, идемпотентные
VFS-команды, outbox, повтор и фоновая reconciliation. Потеря ответа ACL Provider после успешной команды не должна
создавать дублирующие правила при повторе.

Fail-safe поведение:

- ссылка без ACL-доступа не открывает исходный ресурс;
- ACL-доступ без строки таблицы не появляется в `shared`;
- `pending` не показывается получателю;
- `revoking` сразу скрывается;
- ошибка инфраструктуры не превращается в разрешение;
- недоступный исходный URI переводит ссылку в `broken` или скрывает её.

## 14. Безопасность

Реализация должна обеспечивать:

- actor берётся только из доверенного request context;
- Shared не вызывает Auth напрямую и не читает `users`; subject получателя проверяется владеющим Auth/ACL-контуром;
- `target_uri` проверяется через общий parser канонических URI;
- ссылки на provider `shared` запрещены, чтобы не создавать циклы проекций;
- alias не может содержать `..`, NUL, разделители вне выбранной модели и другие
  формы обхода пути;
- поиск ссылки всегда ограничен текущим actor;
- пользователь не может увидеть чужой `incoming` или `outgoing`, подменив путь;
- исходный provider вызывается только через `BoundVFS`;
- проверка существования ссылки не заменяет проверку ACL;
- внешняя ошибка ACL или VFS приводит к fail-closed поведению;
- ACL `allow` разрешает VFS Core вызвать target provider, но не обходит его доменную валидацию и не преодолевает backend `deny`.

## 15. Первая версия

Первая версия поддерживает:

- sharing между зарегистрированными пользователями;
- файлы и каталоги;
- профили `viewer` и `editor`;
- рекурсивный доступ к каталогам;
- `incoming` и `outgoing`;
- команды `create`, `update`, `revoke` через `Control`;
- делегирование содержимого через `BoundVFS`;
- обновление target URI через lifecycle;
- восстановление `pending`, `revoking` и `broken`.

Не входят в первую версию:

- публичные ссылки;
- гостевой доступ;
- sharing на группы;
- срок действия;
- пароль на ссылку;
- принятие или отклонение приглашения;
- перемещение между разными shared-ссылками;
- provider-specific sharing внешней системы.

Эти возможности могут быть добавлены позднее без изменения фундаментальных
контрактов Auth, ACL и VFS Core.

## 16. Критерии готовности

Решение считается реализованным, когда выполняются сценарии:

1. Alice создаёт файл в любом провайдере.
2. Alice вызывает `Control("create")` в своём `shared@me`.
3. Bob видит активную ссылку в `incoming`.
4. Bob открывает содержимое через VFS Core, а не через прямой вызов backend.
5. Существующая строка без разрешения не даёт доступ.
6. Разрешение без строки не появляется в `shared`.
7. Alice меняет профиль через `Control("update")`.
8. Alice отзывает ссылку через `Control("revoke")`.
9. Исходный ресурс после revoke не удаляется.
10. Move или rename исходного URI сохраняет ссылку через lifecycle.
11. Delete исходного URI удаляет или ломает ссылку без передачи её новому ресурсу.
12. Удаление или отключение Shared Provider не меняет работу Auth, ACL и VFS Core.
