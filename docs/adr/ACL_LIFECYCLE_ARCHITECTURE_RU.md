# ADR-003: ACL lifecycle, журнал изменений и overlay

> Статус: принятое целевое архитектурное решение, не описание готовой реализации.  
> Дата решения: 19 сентября 2026 года.  
> Связанные документы: [концепция ACLv2](../ACL_V2_CONCEPT_RU.md), [текущая реализация VFSv2](../VFS_V2_IMPLEMENTATION_RU.md).

## 1. Контекст и цель

ACL хранит и проверяет права относительно канонического VFS URI. В универсальном
контракте нет глобального `resource_id`: внутренние идентификаторы конкретного
провайдера не становятся идентичностью ACL и не попадают в правила доступа.

URI ресурса может измениться при переименовании или перемещении, исчезнуть при
удалении и позднее использоваться новым ресурсом. ACL lifecycle поддерживает
согласованность правил при таких изменениях.

Lifecycle решает четыре задачи:

1. Регистрирует необходимое ACL-состояние только после успешного создания.
2. Сохраняет прямые правила при переименовании или перемещении URI.
3. Немедленно применяет наследование от нового расположения ресурса.
4. Не позволяет удалённому ресурсу передать свои права новому ресурсу с тем же URI.

Lifecycle не принимает решение о доступе. Решение всегда принимает ACL, а
защищённую операцию маршрутизирует VFS Core. Провайдер сообщает только факты об
изменении своего пространства имён.

## 2. Решение

Принята следующая модель:

```text
Системная идентичность ACL  = канонический VFS URI
Непрерывность при move      = durable lifecycle journal
Незавершённая синхронизация = authoritative ACL overlay
Повторное использование URI = ACL generation + tombstone
Provider-local ID           = внутренняя деталь провайдера
Глобальный resource_id      = отсутствует
```

События lifecycle сначала надёжно фиксируются в журнале. Пока основная таблица
ACL ещё не приведена к новому URI, overlay является авторитетной добавкой к ней.
Фоновый materializer переносит правила и сворачивает обработанные изменения.

Обычный in-memory cache не может выполнять роль overlay. Потеря кеша не должна
возвращать ACL к устаревшему состоянию. В памяти допускается только индекс,
полностью восстанавливаемый из durable journal.

## 3. Границы ответственности

| Компонент | Ответственность |
| --- | --- |
| Auth | Устанавливает доверенного `actor` |
| VFS Core | Разрешает URI, проверяет ACL, выполняет операцию через провайдер и инициирует lifecycle |
| Провайдер | Выполняет операцию и сообщает факты об изменении собственного namespace |
| Change supervisor | Принимает внешние change feed, строит доверенные канонические URI и пишет события в журнал |
| Lifecycle journal | Надёжно хранит порядок, состояние и результат мутаций |
| ACL overlay | Делает незавершённые lifecycle-изменения немедленно видимыми ACL |
| ACL evaluator | Принимает окончательное решение по базовым правилам и overlay |
| Materializer | Переносит правила в основное ACL-хранилище и сворачивает overlay |
| Reconciler | Восстанавливает состояние после сбоя и проверяет расхождения с провайдером |

Провайдер не пишет ACL-правила напрямую, не назначает субъектам права и не
становится источником окончательного решения. Полученное от провайдера событие
не является разрешением доступа.

## 4. Источники lifecycle-событий

### 4.1. Операции через VFS Core

Если create, move или delete выполняется через VFS Core, ядро знает actor,
connection и канонические URI операции. Оно создаёт lifecycle intent и связывает
его с вызовом провайдера.

Для staged-записи событие create активируется только после успешного commit.
Отмена загрузки и ошибка commit не должны создавать ACL-состояние.

### 4.2. Изменения вне VFS

Внешний источник может изменить ресурс без вызова VFS: например, пользователь
переименовал файл непосредственно в облачном диске. Для таких подключений
провайдер может реализовать устойчивый change feed:

```go
type NamespaceChange struct {
    EventID     string
    Sequence    uint64
    Kind        ChangeKind
    OldPath     string
    NewPath     string
    IsTree      bool
    ProviderRev string
}

type ChangeFeed interface {
    ReadChanges(
        ctx context.Context,
        cursor string,
        limit int,
    ) (events []NamespaceChange, nextCursor string, err error)
}
```

Это целевой смысл интерфейса, а не обязательная точная форма Go API.

Предпочтителен pull/feed с cursor, а не одноразовый callback:

- после рестарта чтение продолжается с подтверждённого cursor;
- есть backpressure и пакетная обработка;
- событие можно повторить без потери;
- cursor сохраняется только после durable-записи события;
- pooled provider не получает ссылку на ACL или VFS Core.

Change supervisor добавляет `provider`, `connection` и `scope` из доверенной
конфигурации подключения. Провайдер сообщает только provider-local пути и не
может выбрать чужое пространство URI.

Если внешний backend не предоставляет change feed, допустимы только явно
задокументированные режимы:

- все namespace-мутации запрещены вне VFS;
- выполняется периодическая полная reconciliation;
- подключение предоставляет ослабленную гарантию времени согласования.

Нельзя обещать строгую согласованность ACL для внешних изменений, которые нельзя
обнаружить.

### 4.3. Дедупликация двух источников

Одна операция может быть сначала выполнена VFS Core, а затем повторно появиться
в provider change feed. Для дедупликации используются:

- `operation_id` VFS, если backend принимает idempotency token;
- устойчивый `event_id` провайдера;
- монотонный `sequence` или change cursor подключения;
- проверка уже достигнутого состояния при reconciliation.

Provider-local immutable ID допускается внутри адаптера для сопоставления rename
и восстановления change feed. Он не сохраняется в ACL как идентичность ресурса.

## 5. Каноничность URI

URI-based ACL безопасен только при однозначной канонизации. Один ACL-ресурс не
должен быть доступен через несколько неучтённых эквивалентных URI.

Провайдер обязан отвергать неканонические формы либо безопасно возвращать
итоговый канонический путь до доступа к содержимому. Требуется учитывать:

- чувствительность к регистру;
- Unicode-нормализацию;
- percent encoding;
- сегменты `.` и `..`;
- повторные разделители;
- symlink, hardlink и provider-specific alias;
- разные имена одного объекта во внешнем backend.

Если несколько канонических URI намеренно представляют один физический объект,
они считаются разными ACL-контекстами. Это позволяет shared-проекции выдавать
ограниченный доступ без раскрытия исходного дерева. Объединение их прав требует
отдельного явного системного решения и не выводится из provider-local ID.

## 6. Жизненный цикл операции

Lifecycle-операция проходит состояния:

```text
PREPARED -> ACTIVE -> MATERIALIZING -> MATERIALIZED
     |         |
     +-> ABORTED
     +-> RECOVERY <-+
```

Смысл состояний:

| Состояние | Значение |
| --- | --- |
| `PREPARED` | Intent сохранён; затронутые URI защищены от чтения устаревшего ACL |
| `ACTIVE` | Overlay авторитетно отражает новое логическое состояние |
| `MATERIALIZING` | Фоновый worker переносит правила в основное хранилище |
| `MATERIALIZED` | Основное хранилище актуально; overlay можно свернуть |
| `ABORTED` | Провайдер не применил операцию; intent закрыт |
| `RECOVERY` | Результат provider-операции неоднозначен и требуется сверка |

Целевая последовательность move:

1. Выделить `operation_id` и следующую revision подключения.
2. В durable-транзакции записать `PREPARED` и установить prefix fence на source и target.
3. Вызвать `provider.Move`.
4. При явном отказе пометить операцию `ABORTED` и снять fence.
5. При успехе одной durable-транзакцией активировать mapping и source tombstone,
   перевести операцию в `ACTIVE` и снять временный fence.
6. Вернуть успех клиенту: основное ACL-хранилище может быть ещё не переписано, но overlay уже авторитетен.
7. Фоново материализовать правила и закрыть операцию как `MATERIALIZED`.

Если процесс падает между provider commit и `ACTIVE`, prefix fence остаётся
fail-closed, а reconciler проверяет source и target. Общую транзакцию с внешним
провайдером нельзя предполагать.

## 7. Поведение защищённых запросов

Для затронутого URI ACL никогда не должен молча откатываться к устаревшей базовой
таблице.

| Состояние | Поведение запроса |
| --- | --- |
| Нет lifecycle-операции | Обычная проверка базового ACL и активных ACL-дельт |
| `PREPARED` | Короткое ожидание либо контролируемый отказ `synchronization pending` |
| `ACTIVE`/`MATERIALIZING` | Проверка базовых правил вместе с авторитетным overlay |
| `RECOVERY` | Fail-closed для неоднозначно затронутого диапазона |
| Overlay storage недоступен | Отказ, а не fallback к основной ACL-таблице |

Короткое ожидание допустимо только в пределах ограниченного request timeout.
После него возвращается отдельная классифицированная ошибка, а не permission
denied: инфраструктурная неопределённость отличается от отсутствия права.

## 8. Overlay для большого перемещения

При перемещении большого дерева синхронный rewrite всех ACL-строк может быть
слишком дорогим. Критический путь сохраняет одну prefix-операцию:

```text
old_prefix = local@default[alice]:///docs
new_prefix = local@default[alice]:///archive/docs
revision   = 1042
state      = ACTIVE
```

Ресурс уже читается у провайдера по новому URI. Overlay используется только для
логического чтения и изменения ACL, пока materializer переносит физические
строки.

### 8.1. Разделение прямых и наследуемых правил

Нельзя перенаправлять всю ACL-проверку нового URI на старый URI. Для запроса к
`/archive/docs/team/report.pdf`:

- прямые правила старого `/docs/team/report.pdf` продолжают действовать;
- recursive-правила внутри перенесённого `/docs` продолжают действовать;
- наследование от внешних старых родителей больше не действует;
- наследование от новых родителей `/archive` начинает действовать сразу.

Overlay отображает место физического хранения правил поддерева, но ACL evaluator
строит цепочку внешних предков по текущему URI.

### 8.2. Новые grant и revoke во время materialization

Все изменения ACL проходят через logical URI layer. Нельзя позволять сервису
управления ACL писать непосредственно в устаревший физический prefix.

Изменения добавляются как упорядоченные дельты:

```text
100 MOVE   /a -> /b
101 GRANT  user:7 r  /b/x
102 MOVE   /b -> /c
103 REVOKE user:8 w  /c
```

ACL evaluator применяет base, lifecycle mappings и ACL-дельты в порядке revision.
Materializer выбирает фиксированную верхнюю revision, строит результат и перед
фиксацией выполняет compare-and-swap. Устаревший worker не может записать
состояние `/b`, если актуальной целью уже стала `/c`.

## 9. Повторное перемещение и цепочки mapping

Если `/a -> /b` ещё не материализован, операция `/b -> /c` не обязана ждать
полного rewrite. В журнал добавляется следующая revision:

```text
rev 100: /a -> /b
rev 101: /b -> /c
```

До compaction lookup строит композицию:

```text
текущий /c/x -> /b/x -> /a/x -> физические ACL-правила
```

Ограничения цепочки:

- при достижении **4 переходов** запускается приоритетная compaction;
- **6 переходов** — жёсткий максимум на request path;
- операция, которая создала бы седьмой переход, сначала требует синхронной
  compaction затронутой цепочки;
- если compaction сейчас невозможна, move ставится в очередь либо возвращает
  классифицированную ошибку lifecycle backpressure;
- evaluator никогда не продолжает неограниченный обход mapping;
- лимит относится к числу переходов overlay, а не к `generation` URI.

Compactor может сразу свернуть `/a -> /b -> /c` в `/a -> /c`, если revision/CAS
подтверждает, что цепочка не изменилась.

## 10. Конкурентность и prefix locking

Lifecycle сериализует только пересекающиеся URI-диапазоны:

- `/a -> /b` и `/x -> /y` могут выполняться параллельно;
- `/a -> /b` конфликтует с `/a/x -> /c`;
- операции над source и target одного move входят в один lock set;
- перенос `/a -> /a/x` запрещён как цикл;
- swap и перекрывающиеся target требуют составной операции либо временного URI;
- grant/revoke не блокируются на всё время materialization, а записываются как
  новые revision через logical URI layer.

Prefix fence должен быть durable либо восстанавливаться из незавершённых
операций журнала. Обычный process-local mutex недостаточен.

## 11. Generation и повторное использование URI

Последовательность:

```text
delete /a
create /a
```

создаёт новый ACL lifecycle экземпляр URI. Старые правила не должны автоматически
попасть новому ресурсу.

Для этого ACL хранит внутреннюю generation:

```text
/a, generation 17 -> deleted
/a, generation 18 -> active
```

Правило логически относится к `(canonical_uri, generation)`. Delete закрывает
generation tombstone, create открывает следующую. Запоздалое событие generation
17 не может изменить ACL generation 18.

Generation:

- принадлежит ACL lifecycle, а не провайдеру;
- не является глобальным `resource_id`;
- не используется клиентами как адрес;
- не связывает один объект между разными URI;
- защищает URI от повторного использования и запоздалых событий.

Move переносит непрерывность текущей generation со старого URI на новый через
lifecycle operation. Реализация может назначить target собственную generation и
сохранить связь в operation; наружу эта связь не публикуется как identity.

## 12. Delete, create, copy и cross-provider move

### Create

- Initial lifecycle-state создаётся только после успешного provider commit.
- До завершения регистрации новый URI работает fail-closed.
- Повтор события не создаёт новую generation, если совпадает `operation_id`.
- Повторное использование tombstoned URI открывает новую generation.

### Delete

- После provider commit generation закрывается tombstone.
- Прямые правила удаляются либо архивируются асинхронно.
- Tombstone остаётся до тех пор, пока запоздалые события могут быть доставлены.
- Удаление дерева закрывает затронутый prefix и его актуальные поколения.

### Copy

Copy создаёт новый ресурс. Прямые правила источника не копируются автоматически.
Новый URI получает собственную generation и наследует права по месту назначения,
если отдельная продуктовая операция явно не запросила копирование ACL.

### Cross-provider move

Cross-provider move является copy + delete, а не сохранением общей идентичности.
Автоматический перенос прямых ACL-правил требует отдельной авторизованной
политики. Provider-local ID источника не переносится в target connection.

## 13. Служебная модель хранения

Точная SQL-схема определяется реализацией, но логически нужны следующие записи:

```text
acl_namespace_generation
- canonical_uri
- generation
- state: active | moving | deleted
- lifecycle_revision

acl_lifecycle_operation
- operation_id
- connection_key
- sequence
- kind: create | move | delete | resync
- old_uri / old_generation
- new_uri / new_generation
- is_tree
- provider_event_id
- provider_revision
- state
- error_code
- created_at / updated_at

acl_rule_delta
- sequence
- canonical_uri
- generation
- subject_key
- action
- effect
- recursive
- operation: grant | revoke
```

Нужны индексы для:

- поиска операции по `operation_id` и provider event ID;
- получения следующей sequence подключения;
- longest-prefix поиска активного mapping/fence;
- получения дельт до выбранной revision;
- поиска tombstone и текущей generation URI;
- фоновой выборки незавершённых и застрявших операций.

Эти таблицы являются служебным состоянием ACL, а не глобальным реестром ресурсов.

## 14. Materialization и compaction

Materializer работает идемпотентно:

1. Читает immutable snapshot операции и верхнюю revision.
2. Пишет результат в shadow-набор либо применяет повторяемые batch-изменения.
3. Учитывает ACL-дельты до выбранной revision.
4. Проверяет актуальную голову цепочки через CAS.
5. Атомарно публикует результат.
6. Помечает покрытые mapping и дельты materialized.

Частичный batch не должен становиться видимым без overlay. Повторный worker либо
продолжает с checkpoint, либо безопасно начинает batch заново.

Compaction имеет приоритет при:

- четырёх и более переходах mapping;
- большом числе ACL-дельт;
- приближении tombstone retention к пределу;
- высокой стоимости ACL lookup;
- накоплении lifecycle backlog.

## 15. Ошибки и восстановление

Lifecycle различает:

- отказ provider-операции до commit;
- подтверждённый commit и ошибку последующей синхронизации;
- неизвестный результат из-за timeout или потери соединения;
- ошибку ACL storage;
- конфликт revision;
- недоступность change feed;
- lifecycle backpressure.

После подтверждённого provider commit нельзя возвращать ошибку, которая побуждает
клиента слепо повторить исходный move как новую операцию. Ответ должен содержать
стабильный `operation_id` и состояние `committed/synchronization pending` либо
операция должна оставаться доступной для безопасного idempotent retry.

Reconciler:

1. Находит незавершённые операции и непродвинутые provider cursors.
2. Проверяет source/target безопасными metadata-операциями.
3. Использует provider revision или внутренний ID только внутри адаптера, если он доступен.
4. Активирует, отменяет либо оставляет fail-closed неоднозначную операцию.
5. Не выдаёт разрешение на основании догадки.

## 16. Производительность и backpressure

На request path допускаются:

- longest-prefix lookup активного mapping;
- не более шести переходов mapping;
- чтение ограниченного набора ACL-дельт;
- вычисление актуальных предков текущего URI.

В памяти можно держать trie активных prefix mappings. Он является производным
индексом и полностью восстанавливается из журнала.

Если materializer устойчиво отстаёт, система:

1. повышает приоритет compaction;
2. ограничивает новые пересекающиеся move;
3. сообщает lifecycle backpressure;
4. продолжает fail-closed проверки;
5. не удаляет journal ради освобождения места без materialization/checkpoint.

Для небольшого дерева и общей транзакционной БД предпочтителен обычный атомарный
prefix update. Overlay нужен, когда синхронный rewrite нарушает latency, дерево
велико, хранилища разделены или изменения приходят от внешнего провайдера.

## 17. Открытые дескрипторы

Lifecycle гарантирует корректность новых проверок доступа, но сам по себе не
отзывает уже открытый файловый дескриптор. Политика должна быть выбрана отдельно:

- право фиксируется на момент открытия;
- либо handle хранит ACL/generation revision и перепроверяется перед операциями;
- либо lifecycle инвалидирует активные handles затронутого URI-prefix.

До принятия отдельного решения базовой считается проверка на момент открытия.
Это ограничение должно быть явно отражено в API и threat model.

## 18. Наблюдаемость

Минимальные метрики:

- размер lifecycle backlog;
- возраст старейшей незавершённой операции;
- число операций по состояниям;
- длина mapping chain, p50/p95/max;
- число запросов, остановленных prefix fence;
- число fail-closed отказов и recovery;
- lag provider change cursor;
- время materialization и compaction;
- конфликты revision/CAS;
- число операций, остановленных hard limit цепочки.

Аудит хранит actor VFS-операции, canonical old/new URI, operation ID, revisions и
результат. Provider-local ID может присутствовать только как закрытая
диагностическая деталь адаптера и не используется ACL evaluator.

## 19. Критерии готовности и тесты

Реализация считается готовой после проверки как минимум следующих сценариев:

1. Create event появляется только после успешного commit.
2. Abort и commit failure не создают ACL generation.
3. Повтор create/move/delete с тем же operation ID идемпотентен.
4. Rename сохраняет прямые правила.
5. Move немедленно переключает внешнее наследование на новых родителей.
6. Большое дерево доступно через overlay до окончания materialization.
7. Grant/revoke во время materialization не теряется.
8. Второй move образует корректную композицию mapping.
9. При четырёх переходах запускается compaction.
10. Седьмой переход не попадает в request path.
11. Устаревший worker не публикует результат после последующего move.
12. Delete + recreate того же URI не наследует старые прямые правила.
13. Запоздалое событие старой generation игнорируется.
14. Падение на каждом переходе state machine восстанавливается replay/reconciliation.
15. Недоступность overlay не приводит к чтению устаревшего base ACL.
16. Независимые prefix-операции выполняются параллельно, пересекающиеся сериализуются.
17. Provider change feed возобновляется с подтверждённого cursor.
18. Дубликат VFS-события из provider feed не применяется второй раз.
19. Неоднозначный внешний change остаётся fail-closed.
20. Cross-provider copy/delete не переносит ACL без явной политики.

Тесты должны включать property-based последовательности create/move/delete,
конкурентные операции и fault injection между каждым durable и provider-шагом.

## 20. Последствия решения

Положительные последствия:

- ACL остаётся provider-independent;
- глобальный реестр ресурсов не требуется;
- большие move не блокируются полным rewrite ACL;
- внешние изменения можно согласовывать через change feed;
- потеря процесса не означает потерю lifecycle-события;
- shared-проекции сохраняют отдельный ACL-контекст URI.

Цена решения:

- overlay становится обязательной частью пути принятия решения;
- требуются журнал, materializer, reconciler и prefix locking;
- строгая согласованность внешнего provider зависит от его change feed;
- аудит непрерывности объекта сложнее, чем при глобальном immutable ID;
- move поддеревьев требует отдельной логики прямых и наследуемых правил.

Эта цена принимается ради сохранения трёх системообразующих сущностей: Auth, ACL
и VFS Core. Lifecycle является механизмом согласованности ACL, а не четвёртой
глобальной системой идентичности.

## 21. Переход от текущей реализации

Текущий `ResourceLifecycleSink` является только синхронной точкой расширения.
Переход выполняется поэтапно:

1. Ввести типизированное событие с `operation_id`, revision и old/new URI.
2. Заменить непосредственный side effect sink на durable journal writer.
3. Реализовать idempotent обработчики create/move/delete.
4. Добавить generation и tombstone.
5. Подключить overlay к ACL evaluator до реализации асинхронного rewrite.
6. Реализовать materializer, CAS и compaction.
7. Добавить prefix fences/locks и классифицированные lifecycle errors.
8. Добавить optional provider change feed и supervisor.
9. Подключать внешние провайдеры только после проверки cursor/replay semantics.
10. Удалить `NoopResourceLifecycle` из защищённых production-сборок.

До завершения этих шагов существующие callbacks нельзя считать гарантией
согласованности ACL.
