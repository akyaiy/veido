# ACLv2: концепция единой авторизации ресурсов

> Статус: целевая архитектура, не описание готового ACL-модуля. Контекст текущей интеграции сверён с репозиторием на 15 сентября 2026 года, ревизия `948896d0`. Уточнения, требующие решения перед реализацией, выделены отдельно.

## 1. Задача и контекст системы

ACLv2 должен отвечать на один вопрос: **может ли конкретный исполнитель выполнить действие над конкретным ресурсом?**

Приложение представляет ресурсы через VFSv2 — единый интерфейс файлов, каталогов и команд. Провайдер выбирает источник данных: файловое хранилище, БД, доменный сервис или внешнюю систему. HTTP и WebDAV преобразуют запросы клиентов в вызовы VFS. ACL располагается между разрешением адреса ресурса и выполнением защищённой операции.

Например, пользователь читает файл, администратор изменяет настройки подключения, а исполнитель функций читает исходный код. Это разные субъекты и ресурсы, но для них нужен один алгоритм принятия решения.

Цель ACLv2 — единая модель явных разрешений и запретов, наследования по дереву, доступа владельца и общего доступа. Бизнес-валидация, аутентификация пользователя и права внешнего хранилища остаются самостоятельными частями системы.

### Что уже есть в репозитории

- VFSv2 вызывает `Authorizer.Can(ctx, actor, action, ref)`.
- Определены действия `r`, `w`, `x` и типы actor: user, guest, service.
- Существующий `ResourceRef` хранит provider/connection/scope/path без стабильного ID.
- `ACLAuthorizer` сейчас возвращает `true`; отдельные VFSv2-сборки также используют разрешающие заглушки.
- `internal/acl` реализует прежние строковые permissions через группы, wildcard и запреты с `!`. Это другая модель, не реализация ACLv2.
- Таблица ресурсных правил и алгоритм ниже являются концепцией; в просмотренной реализации VFSv2 они не подключены.

Таким образом, этот документ описывает, **что требуется построить и как это должно работать**. Реальная VFSv2 со всеми текущими ограничениями описана в [отдельном файле](VFS_V2_IMPLEMENTATION_RU.md); предварительное чтение того файла для понимания концепции не требуется.

## 2. Модель в одном примере

```text
actor: user:42
адрес: local@default[alice]:///docs/report.md
действие: r
```

Разрешение адреса определяет область `alice`, connection `default` провайдера `local` и файл. Если провайдер поддерживает стабильные ID, путь превращается, например, в ресурс `metadata:105` внутри найденного подключения.

ACL получает исполнителя, действие и идентичность файла. Он собирает применимые правила пользователя и его групп, проверяет сам файл и наследуемые правила предков, затем возвращает разрешение или отказ. Только после успешных проверок VFS передаёт чтение провайдеру.

```text
Аутентификация → actor
Адрес → scope + connection → идентичность ресурса
Actor + действие + идентичность → ACL → разрешить / запретить
Разрешённая операция → провайдер → результат
```

Знание URI и наличие ресурса не являются доказательством права доступа.

## 3. Словарь и границы ответственности

| Понятие | Значение |
| --- | --- |
| Actor | Исполнитель конкретного запроса |
| Subject key | Ключ субъекта ACL: пользователь, группа, гость или сервис |
| Scope | Область ресурсов, внутри которой находятся подключения |
| Connection | Настроенное подключение провайдера с устойчивой идентичностью |
| ResourceRef | Идентичность объекта, по которой сопоставляются правила |
| Action | Одно базовое действие: `r`, `w` или `x` |
| Rule | Разрешение или запрет действия субъекту на ресурсе |
| Recursive | Признак распространения правила на потомков |
| Owner fallback | Неявное разрешение владельцу, используемое при отсутствии применимого явного решения |
| Traverse | Проход через каталог к вложенному ресурсу |

Аутентификация устанавливает actor из доверенного серверного контекста. Резолвер VFS устанавливает, к какому объекту относится адрес. ACL принимает решение о правах. Провайдер выполняет операцию и проверяет её доменную корректность. Например, разрешение `w` не делает невалидный JSON конфигурации допустимым.

## 4. Кто получает права

Основные ключи субъектов:

| Ключ | Назначение |
| --- | --- |
| `user:42` | Конкретный пользователь |
| `group:editor` | Группа, в которую входит пользователь |
| `guest` | Неаутентифицированный исполнитель |
| `all` | Общий субъект; в базовых сценариях включает пользователей и гостей |
| `service:executor` | Внутренний исполнитель функций |
| `service:indexer` | Внутренний сервис индексации |

Для пользователя ACL собирает его ключ, ключи актуальных групп и `all`. Для гостя — `guest` и `all`. Группы должны поступать из доверенного хранилища, а не из произвольного тела запроса.

Сервис действует со своей идентичностью. Переход от пользователя к сервису должен происходить в явно выбранной серверной операции, например при постановке задачи на выполнение функции. `BoundVFS` сам actor не меняет.

В прежних архитектурных заметках состав общих субъектов для сервисов описан неодинаково. До реализации нужно закрепить, включает ли `all` сервисы и нужен ли `all-services`. Примеры ниже используют явные сервисные права и не зависят от этого решения.

`Actor.String()` текущего VFS всегда формирует `kind:id`, тогда как концептуальный гость обозначен `guest`. Нужна явная нормализация субъектов; простое использование всех текущих строк без преобразования не реализует эту модель.

## 5. На что выдаются права

### 5.1. Адрес, отображаемое имя и идентичность

URI нужен клиентам и журналам. Удобное имя WebDAV или shared-путь может измениться. ACL должен опираться на исходную идентичность ресурса.

Целевая ссылка должна содержать:

| Поле | Назначение |
| --- | --- |
| Provider | Тип источника данных |
| Connection identity | Устойчивое подключение, не его отображаемое имя |
| Scope identity | Область ресурса |
| Identity kind | Идентификация по `id` или по `path` |
| Resource ID | ID объекта, если провайдер его поддерживает |
| Path | Текущий путь: идентичность для path-провайдера либо вспомогательные данные для ID-провайдера |

Это логическая структура концепции. Текущий Go `ResourceRef` нужно расширить или дополнить отдельным типом разрешённой идентичности.

Для `local` подходящим кандидатом является `metadata.id`; для внешнего диска — file ID; для проекции сущностей — доменный ID. Если устойчивого ID нет, используется нормализованный путь. Правила всегда ограничены пространством соответствующего provider/connection/scope: совпадение числовых ID в разных пространствах не означает один ресурс.

### 5.2. Переименование и перемещение

При идентификации по ID переименование сохраняет прямые правила на объект. Перемещение также меняет набор предков и поэтому может изменить наследуемые права. Сохранение прямого ACL не означает неизменность итогового доступа.

Для идентификации по пути нужно обновлять правила и индексы при перемещении, включая потомков каталога. Правила удалённого объекта не должны случайно достаться новому объекту с тем же путём или повторно использованным ID.

Если один физический объект доступен через несколько connection, нужно отдельно определить, считаются ли они одним ACL-ресурсом. Базовая модель изолирует их по connection; объединение требует явного правила идентичности.

### 5.3. Родители и владелец

Резолвер идентичности предоставляет упорядоченную цепочку: цель → родитель → следующие предки → корень. Для ID-провайдера цепочка строится по данным источника, для path-провайдера — по сегментам нормализованного пути.

Владелец берётся из доверенных метаданных объекта. Владение scope или членство в группе администратора само по себе не должно незаметно подменять алгоритм ACL. Если нужен административный доступ, он выражается правилами либо отдельно документированной системной политикой.

## 6. Что означают r, w и x

| Тип ресурса | `r` | `w` | `x` |
| --- | --- | --- | --- |
| Файл | Читать содержимое | Изменять содержимое или изменяемые метаданные | Выполнять, если это предусмотрено провайдером |
| Каталог | Перечислять элементы | Изменять состав: создавать, удалять, перемещать элементы | Проходить к вложенному ресурсу |
| Доменная проекция | Читать представление | Изменять через доменную валидацию | Вызывать возможность или команду |
| Scope как ресурс | Видеть сведения об области | Управлять областью | Входить в область для обращения к её ресурсам |

Право `x` на scope не означает `r/w/x` на всё содержимое. Право `r` на каталог также не разрешает читать содержимое каждого файла: для открытия файла нужна отдельная проверка.

### Целевая привязка операций VFS

Ниже — целевая семантика, а не таблица сегодняшних вызовов ядра. До операции требуется вход в scope; для адресации вложенных ресурсов — проход через нужных предков.

| Операция | Целевые проверки |
| --- | --- |
| `Stat` | `r` на цель, `x` на предков |
| `ReadDir` | `r` и `x` на каталог, проход через предков |
| Чтение файла | `r` на файл, `x` на предков |
| Запись существующего файла | `w` на файл, `x` на предков |
| Открытие с чтением и записью | И `r`, и `w` на файл, `x` на предков |
| Создание файла или каталога | `w` и `x` на родителя, проход через предков |
| Удаление элемента | `w` и `x` на родителя, проход через предков |
| Перемещение элемента | `w` и `x` на прежнего и нового родителя, проход по обоим путям |
| `Control` | `x` на ресурс команды или целевую возможность |

Модель изменения состава каталога допускает удаление файла при `w` на родителя даже без `w` на содержимое файла. Это осознанное следствие такой семантики. Если продукту нужен дополнительный запрет удаления на самом объекте, его нужно включить в политику явно и согласовать с таблицей.

При `O_CREATE` система должна различать создание отсутствующей цели и открытие существующей. Для отсутствующего файла ещё нет стабильного ID: первоначальная проверка выполняется по родителю и предполагаемому имени. Для `O_EXCL` право доступа дополняется атомарной проверкой отсутствия в backend; предварительный `Stat` этого не обеспечивает.

Для каталога нужно выбрать политику видимости элементов: показывать все имена при `r` на каталог либо дополнительно скрывать недоступные цели. Само право читать содержимое файла ни в одном варианте не следует из присутствия имени в списке.

## 7. Правило ACL и его хранение

Логическая запись правила:

```text
subject_key = user:17
action      = r
resource    = local / connection-A / alice / id:metadata:105
effect      = allow
recursive   = false
```

Одна запись относится к одному действию. Для выдачи чтения и прохода по дереву нужны соответствующие правила `r` и `x`. `recursive=true` распространяет то же действие на потомков; оно не превращает `r` в `w` или `x`.

Предполагаемое хранилище `resource_acl` содержит субъект, действие, эффект, рекурсивность, идентичность ресурса и служебные поля автора/времени. Это название целевой таблицы; готовой SQL-миграции данный документ не задаёт.

Требования к схеме:

- Допустимые действия — только `r/w/x`, эффекты — `allow/deny`.
- Поиск должен учитывать субъекты actor, запрошенное действие и кандидатов ресурса.
- Уникальность правила должна опираться на нормализованную идентичность. Для ID-ресурса изменяемый путь не должен становиться частью уникального ключа.
- Индексы нужны как для проверки доступа, так и для просмотра/изменения правил конкретного ресурса.
- Изменение правил должно сохранять автора и позволять объяснить происхождение доступа.

Конкретные SQL-поля, замена существующего правила и модель истории требуют реализации. Проверка `Can` не должна создавать новые permissions как побочный эффект чтения правил.

## 8. Алгоритм принятия решения

Для одного `(actor, action, resource)`:

1. Проверить входные данные и построить набор ключей субъекта.
2. Получить идентичность цели, её предков и владельца.
3. Загрузить правила для нужного действия и всех подходящих субъектов.
4. Начать с самой цели. На ней применяются прямые правила независимо от `recursive`.
5. На каждом следующем уровне учитывать только правила с `recursive=true`.
6. На первом уровне, где есть применимые правила, вернуть отказ при наличии `deny`; иначе вернуть разрешение при наличии `allow`.
7. Если на всех уровнях применимых правил нет, применить допустимое правило владельца.
8. Если разрешения по-прежнему нет — отказать.

Ошибка чтения правил или определения идентичности возвращается как ошибка, а защищённая операция не выполняется. Отсутствие разрешения и сбой инфраструктуры — разные результаты, хотя оба останавливают операцию.

### Приоритеты на примерах

| Правила для одного действия | Результат проверки цели |
| --- | --- |
| На `/docs` recursive allow, на `/docs/private.txt` deny | Отказ: ближе правило файла |
| На `/docs` recursive deny, на `/docs/public.txt` allow | Разрешение для файла: его правило ближе |
| На самом файле user allow и group deny, actor входит в группу | Отказ: deny на том же уровне |
| На родителе allow без recursive, других правил нет, actor не владелец | Отказ: правило не распространяется на цель |
| Применимых правил нет, actor — владелец с owner fallback | Разрешение |

Приоритет пользователя над группой отдельно не вводится. Сначала выбирается близость ресурса, затем эффект правила на выбранном уровне.

Разрешение `r` на файл не отменяет отдельный отказ `x` на пути к нему. Поэтому пример с точным allow внутри recursive deny описывает результат одной проверки действия, а не безусловный успех всей файловой операции.

### Правило владельца

Базовая идея — не хранить три ACL-записи на каждый новый объект: владелец может получать `r/w/x` при отсутствии применимых явных правил. Явный запрет owner fallback не обходит.

Нужно отдельно закрепить, кто считается владельцем: только прямой user key, также группа-владелец или иной субъект. Автоматическое наследование владельца от произвольного предка данным алгоритмом не задаётся.

В текущем `local` сохранение файла записывает owner из actor, в том числе при замене существующего содержимого. Перед включением owner fallback необходимо определить, должна ли обычная запись менять владельца. Иначе право редактирования может непреднамеренно привести к получению прав владельца, включая выбранные полномочия управления ACL.

## 9. Scope: вход, видимость и управление

Права на scope проверяются тем же механизмом, что права на остальные ресурсы. Для согласованности с существующим деревом `scopes` в этом концепте предлагается адрес области:

```text
scopes@scopes[system]:///scopes/<scope-key>
```

Это предлагаемая нормализация. Сегодня проверка входа в ядре использует путь `/<scope-key>` и требует `r+w`; это должно быть изменено и покрыто тестами при внедрении.

Целевая последовательность: определить scope → проверить `x` на его идентичность → разрешить connection и цель → проверить нужные действия на цели и предках. Просмотр сведений и изменение области требуют своих `r` и `w`.

Поиск scope должен допускать область, доступную пользователю по ACL, даже если он не владелец. Текущий SQLite-резолвер отсеивает чужой несистемный scope до `Can`, поэтому одной выдачей ACL-прав это ограничение не устранить.

Проверка метаданных самого scope не должна рекурсивно запускать тот же публичный VFS-запрос. Нужен доверенный путь получения идентичности для авторизатора и явное правило начального доступа к системным ресурсам.

## 10. Команды, сервисы и общий доступ

### Запуск функции без чтения исходника

Пример целевых ресурсов, а не существующего VFSv2-провайдера:

```text
functions@system[system]:///resize-image
functions@system[system]:///resize-image/source.go
```

Пользователь получает `x` на функцию. Сервис `service:executor` получает `r` на исходник. Вход в нужную область и проход по пути также должны быть разрешены.

При `Control(..., "run", payload)` сначала проверяется право пользователя вызвать функцию. После принятия задания доверенный исполнитель читает исходник как сервис. Пользователю для этого не требуется право читать код.

`run`, `sync`, `reset-password` не становятся отдельными глобальными действиями ACL. Для раздельных прав на команды нужны раздельные ресурсы возможностей либо явно заданное отображение команды в ресурс. Сейчас несколько SDK-команд на одном URI используют одну проверку `x` этого URI.

### Выдача доступа

Sharing — изменение ACL исходного ресурса. Например, для каталога `metadata:500` получателю `user:17` выдаются recursive `r` и `x`; при необходимости отдельно записывается recursive deny для `w`.

Для выдачи прав нужна отдельная авторизация управления политикой. Право менять содержимое файла не должно автоматически разрешать раздачу доступа. В базовой концепции возможны владелец ресурса и администратор с правом изменять соответствующий ACL-ресурс.

Представление ACL через виртуальные документы требует `w` на ресурс политики. Если используется команда `Control("grant")`, надо согласовать её `x` с проверкой права изменять политику целевого ресурса. Существующие обзоры смешивают эти способы; универсального уже реализованного `grant`-контракта нет.

### Представление shared

Предлагаемый провайдер `shared` строит дерево из доступных ресурсов. Например, `shared@me[bob]:///demo/readme.md` является псевдонимом исходного файла в другом connection.

Открытие должно разрешить псевдоним в исходную идентичность, проверить ACL для текущего actor и обратиться к исходному ресурсу через VFS. Прямые вызовы backend ради обхода запрета недопустимы.

Нужно согласовать sharing с проходом в исходный scope: либо выдать необходимые минимальные права входа и прохода, либо спроектировать отдельный ограниченный контекст доступа к поддереву. В любом варианте доступ к папке не должен автоматически открывать соседние ресурсы. Индекс shared ускоряет поиск, но итоговое решение остаётся за ACL.

### Внешнее хранилище

Для внешнего провайдера операция допустима только при разрешении внутренней политики и внешней системы. Внутренний allow не расширяет права токена Google Drive, S3 или другого источника. Отказ внешней системы остаётся отказом операции даже после успешного `Can`.

## 11. Компоненты, которые потребуются

Имена ниже обозначают роли целевого решения; они не утверждают наличие соответствующих пакетов в репозитории.

| Компонент | Ответственность |
| --- | --- |
| Нормализатор субъектов | Actor → user/guest/service и применимые общие субъекты |
| Поставщик групп | Доверенное членство пользователя в группах |
| Резолвер идентичности | ID или путь цели, упорядоченные предки, владелец |
| Хранилище правил | Чтение и изменение allow/deny с нужными индексами |
| Вычислитель решения | Приоритет уровней, deny, owner fallback, отказ по умолчанию |
| Адаптер `Authorizer` | Подключение решения к вызовам VFSv2 |
| Сервис управления ACL | Авторизация выдачи/отзыва, нормализация правил, история изменений |
| Lifecycle-интеграция | Согласование правил и индексов с изменениями ресурсов |

Резолвер идентичности должен получать метаданные без раскрытия содержимого пользователю и без рекурсивного вызова той же проверки. Операции провайдера после разрешения продолжают выполняться через ядро.

## 12. Согласованность при изменениях

Создание ресурса, изменение его идентичности и изменение правил должны иметь определённый порядок. Текущий VFS вызывает lifecycle sink после успешной операции провайдера; ошибка sink не откатывает данные.

Отсюда следуют требования к реализации ACLv2:

- Для нового staged-файла регистрировать ресурс после успешного commit, а не после начала загрузки.
- При перемещении сохранять прямые правила ID-ресурса и пересчитывать наследование по новым предкам.
- Для path-ресурса переносить связанные записи с определённым поведением при частичном сбое.
- При удалении очищать или помечать недействительными правила и индекс общего доступа.
- Сделать уведомления идемпотентными и предусмотреть восстановление после рассогласования.
- Если появится кеш решений, инвалидировать его при изменении правил, групп, владельца, предков или идентичности подключения.

Данные провайдера и ACL могут находиться в разных хранилищах. Общую транзакцию нельзя считать существующей только из-за интерфейса lifecycle. Механизм согласования — транзакция, журнал событий или восстановление — ещё нужно выбрать.

При проектировании внешних ключей нужно учесть текущую замену файла у `local`: запись metadata удаляется и вставляется заново с тем же ID. Сохранение числового ID не спасёт связанные ACL-записи, если промежуточный `DELETE` вызовет для них каскадное удаление. Эту операцию потребуется согласовать со схемой ACL.

Отдельно нужна политика для уже открытых дескрипторов: текущая VFS проверяет доступ при открытии, а не при каждом `Read`/`Write`. Мгновенный отзыв прав у открытого потока потребует дополнительного механизма.

## 13. Что требуется изменить относительно нынешней VFSv2

| Текущая реализация | Требуемый переход |
| --- | --- |
| `ACLAuthorizer.Can` разрешает всё | Реальное решение на основе субъектов, правил и идентичности |
| Ссылка только по пути | Контракт ID/path, предков и владельца |
| Вход в scope через `r+w` на `/<scope>` | Согласованный scope-ресурс и отдельное право входа |
| SQLite-резолвер принимает только user; явная область — system либо owner | Поддержка выбранных видов actor и доступа по ACL |
| Список scope только по владельцу | Выборка видимых/доступных областей по целевой политике |
| Нет общего прохода с `x` по предкам | Проверки traverse в едином пути выполнения операций |
| Create проверяет `w` несуществующей цели; Delete — `w` цели; Move — также `w` источника | Согласовать и внедрить целевую таблицу из раздела 6 |
| `ReadDir` не фильтрует элементы в ядре | Реализовать выбранную политику видимости |
| Lifecycle обычно no-op | Сохранение и восстановление согласованности ACL |
| Legacy permissions и ACLv2 не связаны | Явная миграция/адаптация нужных правил |

Прежние permissions вида `files.read.*` нельзя автоматически считать эквивалентом recursive `r` на конкретном VFSv2-ресурсе: сначала нужно определить scope, connection и идентичность. Также отличаются приоритеты: legacy сначала обрабатывает совпавшие запреты, а концепция ACLv2 сначала выбирает ближайший уровень ресурса.

При внедрении нужен один понятный источник решения для каждой операции. Параллельные несогласованные проверки старого RBAC, владельца scope и ACLv2 сделают объяснение отказов неоднозначным.

## 14. Открытые решения и критерии готовности

Перед реализацией требуется закрепить:

1. Устойчивую идентичность connection/ресурса, правила повторного использования ID и нескольких ссылок на один объект.
2. Нормализацию гостей и общих субъектов сервисов.
3. Адрес scope-ресурса, начальные системные права и отсутствие рекурсии при проверке входа.
4. Окончательные проверки create/delete/move и видимость элементов каталога.
5. Политику владельца и право управлять ACL, включая интерфейс `grant/revoke`.
6. Проход к shared-ресурсу через исходную область без расширения доступа на соседей.
7. Согласование lifecycle с хранилищами и срок действия решения для открытого дескриптора.

Минимальные сценарии, которыми нужно подтвердить готовую реализацию:

- По умолчанию отказ; разрешение actor не переносится на другого пользователя.
- Прямые и групповые правила, recursive-наследование и deny на одном уровне работают по разделу 8.
- Точное allow не отменяет самостоятельный запрет прохода через предка.
- Read-only доступ к scope не требует права управления им.
- Стабильные прямые права переживают rename; move меняет наследуемую часть доступа.
- Ошибка или отмена загрузки не создаёт ACL-состояние для несохранённого ресурса.
- Sharing не даёт доступ к соседним ресурсам и не обходится через другой псевдоним.
- Пользователь может запускать функцию без чтения исходника; сервис получает отдельные права.
- Ошибка авторизатора останавливает операцию; HTTP и WebDAV дают согласованный результат через одно ядро.

Это критерии будущих тестов, а не заявление о прохождении существующего набора. Концепция считается внедрённой после реализации этих решений и удаления разрешающих заглушек из целевой сборки.
