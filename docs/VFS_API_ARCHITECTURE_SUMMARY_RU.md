# Архитектурное резюме API виртуальной файловой системы

## Назначение

API виртуальной файловой системы дает проекту единый способ обращаться к разным ресурсам как к дереву файлов и каталогов.

Пользователь, внешний клиент или внутренний сервис может работать с локальными файлами, системными сущностями, функциями, общими ресурсами и внешними хранилищами через один понятный язык:

```text
провайдер + подключение + область ресурсов + путь + метод
```

Граница ответственности API виртуальной файловой системы:

- принимает адрес ресурса и файловую операцию;
- распознает адрес и находит конкретный провайдер и область ресурсов;
- передает операцию провайдеру;
- не заставляет внутренние сервисы хранить данные как настоящие файлы.

## Когда используется

Эта модель нужна, когда системе нужно:

- открыть файловую навигацию для интерфейса, WebDAV или API-клиентов;
- дать один контракт для локального хранилища, общих ресурсов, пользователей, функций, Google Drive, S3, GitHub и других провайдеров;
- адресовать ресурсы разных пользователей, проектов или системных областей ресурсов;
- отделить стабильную идентичность ресурса от удобного пути монтирования;
- выполнять специфичные для провайдера команды через `Control`, не превращая строку параметров запроса в набор операций.

## Как работает

Основной поток выглядит так:

1. Клиент передает канонический URI или человеко-ориентированный путь монтирования.
2. VFS определяет исполнителя из контекста.
3. Если пришел путь монтирования, система распознает его внутри текущей области ресурсов.
4. URI разбирается на провайдер, подключение, область ресурсов, путь и параметры запроса.
5. Распознаватель находит итоговую область ресурсов и подключение провайдера.
6. Провайдер получает операцию в своей модели данных.
7. ACL проверяет права на область ресурсов и целевой ресурс.
8. Провайдер выполняет файловый метод или `Control`.
9. VFS возвращает результат в виде файлов, каталогов, содержимого или ошибки.

## Компоненты

- `ResourceURI` описывает внешний адрес ресурса.
- `ResourceResolver` или `VFSRouter` разбирает URI, область ресурсов и подключение.
- `MountManagerFSProvider` превращает пути монтирования в канонический URI.
- `FSProvider` задает общий контракт, похожий на системные вызовы: чтение, запись, получение списка, удаление и перемещение.
- Провайдеры хранения хранят байты и метаданные.
- Провайдеры-адаптеры внешних систем адаптируют внешние API к VFS-контракту.
- Провайдеры-проекции показывают доменную модель приложения как файлы и каталоги.
- ACL-слой решает, можно ли исполнителю выполнить операцию над распознанным ресурсом.

## Пример

Пользователь открывает файл:

```text
/my-343123/home/docs/report.md
```

Система распознает путь:

```text
/my-343123/home/docs/report.md
  -> scope:1 (my-343123)
  -> точка монтирования /home -> драйвер local -> подключение с айди default
  -> local@default[scope:1]:///docs/report.md
  -> ResourceRef(metadata:105)
```

После этого VFS проверяет права на вход в область и чтение файла. Если доступ разрешен, `local` провайдер открывает файл и возвращает содержимое.

## Ограничения

- API виртуальной файловой системы не является требованием хранить все данные как реальные файлы.
- Путь монтирования не считается стабильной идентичностью ресурса.
- Параметры запроса используются только для фильтров, формата, версии или представления, а не для основных операций.
- Обычные операции создания, чтения, изменения и удаления остаются в VFS-методах, а специфичные для провайдера команды идут через `Control` или файлы действия.
- Провайдер сам отвечает за свою внутреннюю семантику и валидацию записи.

## Записи архитектурных решений

### ADR-001: URI начинается с провайдера

#### Контекст

В проекте появляются разные типы ресурсов: локальные файлы, системные сущности, функции, общая надстройка и внешние провайдеры.

#### Проблема

Обычный путь не сохраняет идентичность провайдера и становится неоднозначным для Google Drive, S3, GitHub, системных провайдеров и пользовательских подключений.

#### Варианты

- хранить все ресурсы в одном глобальном пространстве имен путей;
- использовать путь монтирования как основную идентичность;
- сделать канонический URI, который начинается с провайдера.

#### Решение

Использовать формат:

```text
<провайдер>[@<подключение>][\[<область>\]]:///<путь>[?<параметры>]
```

В этой схеме `[...]` означает необязательную часть, а `\[` и `\]` означают настоящие квадратные скобки внутри URI. Часть `[?<параметры>]` тоже необязательная; `?` внутри нее является настоящим символом URI, например `?export=pdf`.

Примеры:

```text
local:///docs/report.md
local@default:///docs/report.md
local@default[scope:1]:///docs/report.md
gdrive@work[scope:1]:///doc123?export=pdf
```

#### Последствия

Ресурс получает стабильный адрес для API, ACL, логов и внутренних сервисов. Пути монтирования остаются удобными псевдонимами для навигации.

### ADR-002: `Control` для команд провайдера

#### Контекст

Некоторые провайдеры должны выполнять команды, которые не являются обычным чтением, записью, удалением или листингом.

#### Проблема

Если складывать команды в строку параметров запроса, URI начинает отвечать не только на вопрос «что это?», но и на вопрос «что сделать?».

#### Варианты

- кодировать операции в параметры запроса;
- создавать отдельные REST-ручки для каждого провайдера;
- добавить похожий на системные вызовы метод `Control`.

#### Решение

Оставить обычные операции создания, чтения, изменения и удаления в VFS-методах, а специфичные для провайдера команды выполнять через `Control` или файлы действия.

Базовая сигнатура:

```go
Control(ctx context.Context, uri ResourceURI, command string, input []byte) ([]byte, error)
```

Примеры вызовов:

```text
Control(gdrive@work[scope:1]:///doc123, "export", {"format":"pdf"})
Control(gdrive@work:///, "sync", {})
Control(functions@system:///resize-image, "run", {"input":"..."})
Control(users@system:///"admin - 1", "reset-password", {"newPassword":"..."})
Control(local@default[scope:1]:///video.mp4, "thumbnail", {"time":"00:01:20"})
```

Здесь URI отвечает на вопрос «над каким ресурсом работаем», `command` отвечает на вопрос «какую команду провайдера выполнить», а `input` передает параметры команды.

#### Последствия

Методы, путь и параметры запроса сохраняют ясные роли. Клиенты, которые работают через файловую модель, могут использовать файлы действия. Клиенты, которые работают напрямую с API, могут использовать `Control`.

### ADR-003: Корень `/` как динамическая навигация по областям ресурсов

#### Контекст

Раньше пользовательский корень фактически означал домашнюю папку в `local`: пользователь открывал `/` и попадал в локальное файловое дерево своей домашней области. В новой модели есть несколько областей ресурсов, несколько подключений провайдеров и внешние системы вроде Google Drive, S3, GitHub, системных функций и общих ресурсов.

#### Проблема

Если оставить `/` домашней папкой `local`, то `local` останется скрыто особым провайдером, а остальные провайдеры придется монтировать вокруг него. Это снова делает локальную файловую систему центром архитектуры и плохо отражает модель, где главный объект навигации - область ресурсов, а внутри нее уже находятся подключения провайдеров.

#### Варианты

- оставить `/` домашней папкой `local`;
- показывать в `/` глобальное дерево всех системных ресурсов;
- сделать `/` динамическим списком областей ресурсов, доступных текущему исполнителю.

#### Решение

Сделать пользовательский `/` динамическим каталогом:

```text
/
  my-343123/
  archive-771204/
  project-acme-9981/
  shared-from-alex-5502/
```

Первый уровень загружает доступные области ресурсов. Второй уровень внутри выбранной области загружает доступные точки монтирования и подключения провайдеров:

```text
/my-343123/
  home/          -> local@default[scope:1]:///
  gdrive/        -> gdrive@work[scope:1]:///
  shared/        -> shared@me[scope:1]:///
  functions/     -> functions@system:///
```

После выбора точки монтирования пользователь попадает в реальную систему провайдера:

```text
/my-343123/home/docs/a.txt
  -> local@default[scope:1]:///docs/a.txt

/my-343123/gdrive/report.docx
  -> gdrive@work[scope:1]:///My Drive/report.docx
```

`local` больше не является корнем всех систем. Это обычный провайдер наравне с `gdrive`, `s3`, `github`, `users`, `functions` и `shared`.

#### Последствия

Корень `/` становится навигационным представлением, а не стабильной идентичностью ресурса. Канонический URI и `ResourceRef` остаются внутренними стабильными адресами. WebDAV и файловые менеджеры получают удобное дерево, но ACL, API, логи и внутренние сервисы работают через распознанный URI.

## Словарь технических имен

- `VFS` - виртуальная файловая система.
- `ACL` - список правил доступа.
- `URI` - адрес ресурса.
- `scope` - настоящий ключ в URI и таблицах для области ресурсов, например `[scope:1]` и `scope_id`.
- `provider` - провайдер; в URI и именах таблиц это техническое имя.
- `ResourceRef` - нормализованная ссылка на ресурс для ACL и долговечных ссылок.
- `Control` - метод для команд провайдера, которые не являются обычными файловыми операциями.
- `FSProvider`, `ResourceResolver`, `VFSRouter`, `MountManagerFSProvider` - имена интерфейсов и компонентов в коде.

## Детали реализации

### Основная идея

API проекта можно представить как Unix-подобную виртуальную файловую систему.

Внешние клиенты не обязаны напрямую дергать множество разрозненных REST-ручек. Они могут работать с ресурсами через дерево каталогов и файлов:

```text
users@system:///"admin - 1"/userdata.json
functions@system:///resize-image/source.go
shared@me:///project/file.md
gdrive@work:///My Drive/report.docx
```

Это не означает, что внутри все должно быть реализовано как реальные файлы. Файловая модель здесь является внешним языком API. Внутри провайдеры могут использовать БД, сервисы, облачные API, auth-модули, раннеры функций или обычное файловое хранилище.

### 2. Почему это подходит текущему проекту

В проекте уже есть подходящая база:

- `internal/vfs` задает базовый VFS-слой.
- `FSProvider` уже предоставляет файловые операции:
  - `ResolvePathToID`
  - `ReadDir`
  - `OpenFile`
  - `Stat`
  - `Mkdir`
  - `Move`
  - `Delete`
- `MountManagerFSProvider` уже маршрутизирует операции через смонтированные провайдеров.
- WebDAV уже адаптирует VFS во внешний протокол.
- `/api/files/acc2fs` уже открывает VFS-операции через HTTP.
- `SharedFSProvider` уже доказывает, что провайдеры могут показывать динамические виртуальные ресурсы без собственного хранения реальных файлов.

Значит, архитектуру не нужно придумывать с нуля. Ее нужно явно оформить и обобщить.

### 3. Важный вывод из SharedFSProvider

`SharedFSProvider` сейчас является лучшим примером провайдер-проекция и провайдер-надстройка.

Он сам не хранит файлы. Вместо этого он:

1. Показывает пользователю виртуальное дерево.
2. Резолвит виртуальные пути в настоящие VFS node ID.
3. Делегирует реальные операции в связанный провайдер.
4. Возвращает вызывающему коду виртуальные пути.

Концептуально:

```text
SharedFSProvider:
  virtual путь -> real VFS node id -> bindПровайдер операция
```

Тот же паттерн можно использовать для системных модулей:

```text
UsersFSProvider:
  virtual путь -> user id / field / action -> auth/db/service операция

FunctionsFSProvider:
  virtual путь -> function name / исходник / action -> function service операция

GDriveFSProvider:
  virtual путь -> внешний file ID / folder id -> внешний провайдер API операция
```

То есть `FSProvider` подходит не только для провайдеров хранилища. Он также подходит для динамических проекций состояния приложения.

### 4. Типы провайдеров

Полезное разделение:

```text
Провайдеры хранения:
  LocalFSProvider
  HostFSProvider

Провайдеры-адаптеры внешних систем:
  GDriveFSProvider
  S3FSProvider
  GitHubFSProvider
  WebDAVProvider

Провайдеры-проекции:
  UsersFSProvider
  FunctionsFSProvider
  ACLProvider
  HTMLBlocksProvider

Провайдеры-надстройки и маршрутизирующие провайдеры:
  SharedFSProvider
  MountManagerFSProvider
```

Storage провайдер в основном хранит байты и метаданные.

Remote adapter провайдер адаптирует внешнюю систему с собственной моделью к контракту `FSProvider`.

Провайдер проекции показывает доменную модель приложения как файлы и каталоги.

Маршрутизирующий провайдер распознает пути или URI в нужный провайдер.

### 5. Каноническая URI ресурса-модель

Предпочтительная модель: сначала провайдер.

```text
<провайдер>[@<подключение>][\[<область>\]]:///<путь>[?<параметры>]
```

В этой схеме `[...]` означает необязательную часть, а `\[` и `\]` означают настоящие квадратные скобки внутри URI. Часть `[?<параметры>]` тоже необязательная; `?` внутри нее является настоящим символом URI, например `?export=pdf`.

Примеры:

```text
local@default:///home/user/a.txt
shared@me:///project/file.md
users@system:///"admin - 1"/userdata.json
functions@system:///resize-image/source.go
gdrive@work:///My Drive/report.docx
s3@assets-bucket:///images/logo.png
github@triggerssmith:///JWTproject2/main/internal/vfs/vfs.go
gdrive@work[user:42]:///My Drive/report.docx
```

Смысл:

```text
провайдер          = тип провайдера: local, shared, users, functions, gdrive, s3, github
подключение        = необязательный экземпляр провайдера: аккаунт, bucket, repo или имя подключения
scope              = необязательный явный селектор области ресурсов, например [scope:1] или [user:42]
путь               = путь ресурса внутри подключения провайдера
параметры запроса  = модификаторы чтения, списка, статуса или открытия, а не основная операция
```

Это убирает неоднозначность, когда у разных провайдеров разная семантика.

Например:

- В Google Drive могут быть одинаковые имена и важные file IDs.
- В S3 есть object keys, а не настоящие директории.
- В GitHub запись может означать commit.
- Системные провайдеры могут открывать actions, которые меняют состояние приложения.
- Локальные файлы ближе к POSIX.

URI должен сохранять идентичность провайдера, а не прятать все внутри одного обычного пути.

### 6. Пути монтирования как псевдонимы

Пути монтирования все еще полезны, но их лучше считать псевдонимами, а не канонической идентичностью ресурса.

Примеры:

```text
/home                  -> local@default:///home/user
/shared                -> shared@me:///
/system/users          -> users@system:///
/system/functions      -> functions@system:///
/cloud/google/work     -> gdrive@work:///
/projects/acme/drive   -> gdrive@client-acme:///
```

Правило:

```text
Канонический URI - стабильная идентичность.
Путь монтирования - удобный навигационный псевдоним.
```

Так сохраняется ощущение, похожее на Unix, но не появляется хаос от произвольного монтирования системных ресурсов внутрь любых пользовательских папок.

### 7. Методы, путь, параметры запроса и `Control`

VFS должен сохранять разделение, похожее на системные вызовы:

```text
метод + URI + настройки
```

Метод выражает операцию:

```text
ReadDir(ctx, uri)
OpenFile(ctx, uri, flags)
Stat(ctx, uri)
Mkdir(ctx, uri)
Move(ctx, oldURI, newURI)
Delete(ctx, uri)
Control(ctx, uri, command, input)
```

Путь выражает целевой ресурс:

```text
users@system:///"admin - 1"/userdata.json
functions@system:///resize-image/source.go
gdrive@work:///My Drive/report.docx
```

Параметры запроса выражают модификатор, фильтр, версию, формат или представление:

```text
users@system:///?status=active
gdrive@work:///doc123?export=pdf
github@repo:///file.go?ref=main
s3@bucket:///file.txt?versionId=abc
```

Не стоит использовать параметры запроса вместо методов.

Плохо:

```text
users@system:///"admin - 1"/userdata.json?op=писать
users@system:///?op=список
functions@system:///resize?run=true
```

Хорошо:

```text
OpenFile(users@system:///"admin - 1"/userdata.json, O_WRONLY)
ReadDir(users@system:///?status=active)
Control(functions@system:///resize, "run", input)
```

Короткое правило:

```text
Путь отвечает: что это за ресурс?
Метод отвечает: что сделать?
Параметры запроса отвечают: какое представление, версия, фильтр или режим нужны?
Control отвечает: какую специфичную для провайдера команду выполнить?
```

### 8. Параметры запроса как легкий аналог `ioctl`

`параметры запроса` можно считать легким декларативным родственником `ioctl`, но только для модификаторов.

Хорошее использование параметров запроса:

```text
gdrive@work:///doc123?export=pdf
github@project:///file.go?ref=main
s3@bucket:///file.txt?versionId=abc
users@system:///?status=active
```

Плохое использование параметров запроса:

```text
users@system:///admin?do=ban
local@default:///a.txt?delete=true
functions@system:///resize?run=true
```

Это команды, а не модификаторы представления. Им место в `Control`, файлах действия или обычных VFS-методах.

### 9. Метод Control

`Control` полезен, и его стоит добавить как механизм специфичных для провайдера команд.

Возможная форма:

```go
Control(ctx context.Context, id ResourceID, command string, in []byte) ([]byte, error)
```

Или, если URI-модель вводится напрямую:

```go
Control(ctx context.Context, uri ResourceURI, command string, in []byte) ([]byte, error)
```

Нормальные сценарии:

```text
Control(gdrive@work[scope:1]:///doc123, "export", {"format":"pdf"})
Control(gdrive@work:///, "sync", {})
Control(functions@system:///resize-image, "run", {"input":"..."})
Control(users@system:///"admin - 1", "reset-password", {"newPassword":"..."})
Control(local@default[scope:1]:///video.mp4, "thumbnail", {"time":"00:01:20"})
```

Граница:

```text
Если это обычное поведение файла или каталога, используем обычный VFS-метод.
Если операция читает или пишет содержимое файла, используем OpenFile.
Если операция управляет специфичным для провайдера поведением или запускает возможность провайдера, используем Control.
```

Обычный обычные операции создания, чтения, изменения и удаления не стоит складывать в `Control`.

### 10. Действие-файлы

Некоторые команды можно также представить как специальные файлы:

```text
functions@system:///resize-image/run.action
users@system:///"admin - 1"/password.action
gdrive@work:///.sync.action
```

Это полезно, когда команда хорошо ложится в файловую метафору и должна быть доступна клиентам, которые работают через файловую модель.

Рекомендуемое различие:

```text
Control:
  внутренний/Работающие напрямую с API провайдер command

*.файлы действия:
  файловый фасад команды для клиентов и интерфейса
```

Оба варианта могут вызывать одну и ту же внутреннюю service logic.

### 11. Пример Users Провайдер

Возможное дерево пользователей:

```text
users@system:///
  "admin - 1"/
    userdata.json
    groups.json
    ключи прав.json
    password.action
    sessions/
  "user1 - 2"/
    userdata.json
```

Поведение:

```text
ReadDir(users@system:///)
  выводит пользователей как виртуальные каталоги

OpenFile(users@system:///"admin - 1"/userdata.json, O_RDONLY)
  возвращает динамический JSON из БД

OpenFile(users@system:///"admin - 1"/userdata.json, O_WRONLY)
  принимает JSON, валидирует его и применяет изменения через сервис пользователей

Delete(users@system:///"admin - 1")
  удаляет или отключает пользователя, в зависимости от выбранной семантики

Control(users@system:///"admin - 1", "reset-password", input)
  выполняет специфичную для провайдера команду пользователя
```

Важная деталь:

Запись в `userdata.json` не означает, что байты слепо сохраняются. Провайдер принимает предложенное новое представление, валидирует его и применяет разрешенные изменения. Если валидация не проходит, запись возвращает ошибку.

### 12. Несколько подключений одного типа провайдер

Один пользователь может подключить несколько инстансов одного и того же типа провайдер. Google Drive здесь только пример; то же правило относится к S3, GitHub, WebDAV, внешним БД, проектным хранилищам и другим провайдеров.

`@подключение` используется как имя подключения в текущем пользовательском контексте:

```text
gdrive@personal:///
gdrive@work:///
s3@assets:///
s3@backups:///
github@main-org:///
github@client-acme:///
```

Для пользователя `42`:

```text
gdrive@personal:///...     -> подключение(default-scope(user:42), провайдер:gdrive, name:personal)
gdrive@work:///...         -> подключение(default-scope(user:42), провайдер:gdrive, name:work)
s3@assets:///...           -> подключение(default-scope(user:42), провайдер:s3, name:assets)
github@client-acme:///...  -> подключение(default-scope(user:42), провайдер:github, name:client-acme)
```

Для пользователя `17` тот же видимый URI может распознаться в его собственное подключение:

```text
gdrive@personal:///...     -> подключение(default-scope(user:17), провайдер:gdrive, name:personal)
s3@assets:///...           -> подключение(default-scope(user:17), провайдер:s3, name:assets)
```

Значит, `gdrive@personal:///` или `s3@assets:///` уникален внутри текущего контексте безопасности, а не глобально.

Администратор может явно адресовать подключение другого пользователя через `scope`:

```text
gdrive@work[user:42]:///My Drive/report.docx
s3@assets[user:42]:///images/logo.png
github@client-acme[user:42]:///repo/main/a.go
```

Рекомендуемые нормализованные таблицы:

```text
scopes
  id
  kind                 // вид области ресурсов: personal, system, org, project, team, service
  slug                 // короткое имя: main, archive, acme, backend
  display_name         // имя для интерфейса
  owner_subject_key    // правило владельца: user:42, org:3, system
```

```text
principal_default_scopes
  principal_type
  principal_id
  purpose
  scope_id
```

```text
provider_connections
  id
  scope_id
  provider_type      // тип провайдера: gdrive, s3, github и т.д.
  connection_name    // имя подключения: personal, work, assets, client-acme
  config_json        // настройки подключения
```

Рекомендуемая уникальность:

```text
UNIQUE(scope_id, provider_type, connection_name)
```

Это позволяет:

- одному пользователю иметь много подключений одного типа провайдер;
- разным пользователям переиспользовать имена вроде `personal` или `work`;
- одному пользователю иметь несколько областей ресурсов, и в каждом свои подключения провайдера;
- серверу сохранять однозначный канонический resolution.

### 13. Поведение корня провайдер

Полезное поведение:

```text
ReadDir(gdrive:///)
ReadDir(s3:///)
ReadDir(github:///)
```

Возвращает подключения текущего пользователя для этого типа провайдер:

```text
personal/
work/
client-acme/
assets/
backups/
```

Дальше:

```text
ReadDir(gdrive@work:///)
ReadDir(s3@assets:///)
ReadDir(github@client-acme:///)
```

Листит корень конкретного подключения провайдер.

Это дает чистую навигационную модель:

```text
gdrive:///                          список my Google Drive подключения
gdrive@work:///                     корень of my work Drive подключение
gdrive@work:///My Drive/a.txt       файл внутри этого подключения

s3:///                              список my S3 подключения
s3@assets:///images/logo.png        объект внутри подключения assets

github:///                          список my GitHub подключения
github@client-acme:///repo/main/a.go файл внутри подключения client-acme
```

### 14. Внутренние стабильные ссылки

URI для людей могут быть зависящими от контекста:

```text
gdrive@work:///My Drive/a.txt
```

Для внутренних долговечных ссылок лучше использовать подключение ID или провайдер resource ID:

```text
gdrive@conn-8842:///My Drive/a.txt
gdrive@conn-8842:///file-id:abc123
gdrive@work:///file-id:abc123
```

URI для людей:

```text
gdrive@work:///My Drive/a.txt
```

Распознанная внутренняя идентичность:

```text
provider_type = gdrive
connection_id = 8842
external_file_id = abc123
```

UI обычно должен показывать человекочитаемые имена. Сервер должен хранить стабильные ID там, где важны долговечные ссылки.

### 15. Пространства имен точек монтирования

Точки монтирования, скорее всего, должны быть scoped, а не чисто глобальными.

Возможная таблица `mount_points`:

```text
mount_points
  scope_id
  mount_path
  target_uri
  flags
```

Примеры:

```text
scope:1, область ресурсов пользователя 42 по умолчанию:
  /cloud/google/personal -> gdrive@personal:///
  /cloud/google/work     -> gdrive@work:///

scope:2, область ресурсов пользователя 17 по умолчанию:
  /cloud/google/personal -> gdrive@personal:///
```

Один и тот же путь монтирования может означать разные вещи для разных пользователей, потому что он распознается внутри их пространства имен.

### 16. Три режима адресации

Есть три практических способа обращаться к VFS-ресурсам.

#### 1. Канонический URI

Канонический URI - основной внутренний/API-адрес:

```text
local@default[scope:1]:///projects/demo
gdrive@work[scope:1]:///My Drive/report.docx
functions@system:///resize-image
shared@me:///demo/readme.md
```

Его стоит использовать для:

```text
браузерных клиентов
внутренних сервисов
ACL-распознавания ресурсов
логов и аудита
долговечных API-ссылок
```

Внутри все неканонические способы адресации должны сначала распознаться в канонический URI, а затем в стабильный `ResourceRef`.

#### 2. Пространство имен путей области ресурсов

Этот режим является следствием `ADR-003`: пользовательский корень `/` - динамическое дерево областей ресурсов и подключений, а не домашняя папка `local`.

Для WebDAV, файловых менеджеров, ручного просмотра и отладки интерфейса можно открыть простое пространство имен путей:

```text
/{scope-name-id}/{mount}/...
```

Не стоит делать пользовательский путь вида `/области/1/...`. Имя области должно быть уникальным только в списке областей ресурсов, видимых текущему исполнителю, а общие области ресурсов тоже могут попадать в этот список. Поэтому лучше использовать человекочитаемые и устойчивые к конфликтам псевдонимы:

```text
/my-343123/home/projects/demo
/archive-771204/home/old/a.txt
/project-acme-9981/gdrive/report.docx
/shared-from-alex-5502/home/demo/readme.md
```

Внутри пространства имен области ресурсов следующий сегмент пути - это псевдоним точки монтирования:

```text
/my-343123/home/...       -> local@default[scope:1]:///...
/my-343123/gdrive/...     -> gdrive@work[scope:1]:///...
/my-343123/shared/...     -> shared@me[scope:1]:///...
```

Если цель точки монтирования не содержит явную область ресурсов:

```text
/my-343123/home/a.txt
  -> /my-343123 распознается как scope:1
  -> /home распознается как local@default:///
  -> итоговый канонический URI: local@default[scope:1]:///a.txt
```

#### 3. Список корневых областей ресурсов

Открытие `/` не должно показывать глобальный файловый корень или домашнюю папку `local`. Оно должно показывать области ресурсов, доступные текущему исполнителю:

```text
/
  my-343123/
  archive-771204/
  project-acme-9981/
  shared-from-alex-5502/
```

Чтобы область ресурсов появилась в `/`, исполнитель должен иметь хотя бы видимость или доступ к ней:

```text
Can(исполнитель, r, scope@system:///scopes/{scope_id})
or
Can(исполнитель, x, scope@system:///scopes/{scope_id})
```

Для WebDAV обычно проще показывать только области ресурсов с `x`, потому что клиенты ожидают, что видимые папки можно открыть.

Правило:

```text
/                                 -> список доступных областей ресурсов
/{scope-name-id}/                 -> список точек монтирования внутри этой области ресурсов
/{scope-name-id}/{mount}/...      -> упрощенный путь через пространство имен точек монтирования
провайдер@conn[scope]:///...       -> канонический URI
ResourceRef                       -> стабильная ACL-идентичность
```

Важно:

```text
Пространства имен путей являются удобным сокращением.
Канонический URI - внутренний адрес.
ResourceRef - ACL-идентичность.
```

Для браузерных клиентов и внутренних API лучше использовать канонический URI. Для WebDAV и человеко-ориентированного файлового просмотра - упрощенное пространство имен путей.

### 17. Многопользовательская VFS-модель

Новая URI-модель меняет старое допущение, что любой VFS-путь распознается относительно домашней области текущего пользователя.

Теперь лучше явно разделять:

```text
actor = кто выполняет операцию
scope = чье пространство имен и подключение провайдера адресуются
target = конкретный URI ресурса
```

Пример:

```text
local@default:///docs/a.txt
```

Для пользователя `42` это означает:

```text
actor = user:42
scope = неявная область ресурсов user:42
provider = local
connection = default
path = /docs/a.txt
```

Администратор может явно обратиться к пространству имен `local` другого пользователя:

```text
local@default[user:17]:///docs/a.txt
```

Это означает:

```text
actor = user:42
scope = user:17
target = local default connection пользователя 17
```

Проверка прав должна звучать так:

```text
Can user:42 perform action X on resource local@default[user:17]:///docs/a.txt?
```

Это отличается от текущего допущения `FSManager`:

```text
текущий пользователь -> home node id -> все пути считаются относительно его домашнего каталога
```

Новая модель:

```text
текущий исполнитель -> разбор URI -> распознавание итоговой области ресурсов -> распознавание подключения провайдера -> авторизация -> вызов провайдера
```

### 18. `local` как провайдер внутри области ресурсов

В этой модели `local` больше не является глобальным VFS-корнем. Это подключение провайдера внутри конкретной области ресурсов.

Если область ресурсов не указана, `local@default:///` наследует итоговую область ресурсов от исполнителя или из упрощенного пути.

Для исполнителя `user:42`:

```text
local@default:/// -> область ресурсов user:42 по умолчанию -> provider_connection(scope:1, local, default)
```

Для исполнителя `user:17`:

```text
local@default:/// -> область ресурсов user:17 по умолчанию -> provider_connection(scope:2, local, default)
```

Если область ресурсов указана явно:

```text
local@default[scope:1]:///docs/a.txt
  -> provider_connection(scope:1, local, default)

local@default[user:17]:///docs/a.txt
  -> область ресурсов user:17 по умолчанию
  -> provider_connection(scope:2, local, default)
```

Обычный корневой путь `/` не является корнем `local`. Он показывает доступные области ресурсов:

```text
/
  my-343123/
  project-acme-9981/
  shared-from-alex-5502/
```

Точки монтирования появляются уже внутри выбранной области ресурсов:

```text
/my-343123/home   -> local@default[scope:1]:///
/my-343123/shared -> shared@me[scope:1]:///
```

Так `local` остается обычным провайдером, а пользовательский `/` остается удобным просмотрщиком областей ресурсов для WebDAV и файлового просмотра.

### 19. Где хранить область ресурсов и как связать ее с ACL

`scope` не должна жить внутри пути. Ее нужно разобрать из URI и распознать в нормализованную запись области ресурсов.

```go
type AreaRef struct {
    ID   int64
    Kind string // personal, system, org, project, team, service
    Slug string // main, archive, acme, backend
}
```

Если область ресурсов не указана:

```text
scope = область ресурсов исполнителя по умолчанию
```

Примеры:

```text
local@default:///docs/a.txt
  -> область ресурсов исполнителя

local@default[user:17]:///docs/a.txt
  -> явная область ресурсов user:17

users@system:///
  -> системная область ресурсов
```

Области ресурсов лучше сделать полноценными ресурсами:

```text
scopes
  id
  kind                 // personal, system, org, project, team, service
  slug                 // main, archive, acme, backend
  display_name
  owner_subject_key    // optional правило владельца: user:7, org:3, system
  created_at
  updated_at
```

Важное правило:

```text
области ресурсов задают пространства ресурсов.
ACL определяет, кто может входить, читать, управлять или делегировать эти пространства.
```

Не стоит создавать вторую систему авторизации вроде `scope_owners`, если это не просто служебные данные. Доступ к области ресурсов должен проверяться через ту же ACL-модель, что и доступ к любому другому ресурсу.

Область ресурсов можно представить как ACL-ресурс:

```text
scope@system:///scopes/42
```

Рекомендуемая семантика прав на область ресурсов:

```text
r = видеть область ресурсов и выводить ее в списке
w = менять настройки области ресурсов, точки монтирования и подключения провайдера
x = войти в область ресурсов и использовать ее как итоговую цель
```

Примеры ACL-проверок:

```text
Can(user:42, x, scope@system:///scopes/17-main)
Can(user:42, w, scope@system:///scopes/17-main)
Can(group:admin, x, scope@system:/// recursive)
```

`owner_subject_key` нужен только как правило владельца, совместимый с идеей owner-default из ACL-дока:

```text
явный запрет сильнее правила владельца
правило владельца сильнее запрета по умолчанию
```

Подключения провайдера должны ссылаться на `scope_id`, а не хранить `owner_type/owner_id` напрямую:

```text
provider_connections
  id
  scope_id
  provider_type      // local, gdrive, s3, functions, users, shared
  connection_name    // имя подключения: default, work, system, me, assets
  config_json
  status
  created_at
  updated_at
```

Рекомендуемая уникальность:

```text
UNIQUE(scope_id, provider_type, connection_name)
```

Примеры записей:

```text
scope_id  provider_type  connection_name  config_json
1         local          default          {"root_node_id":"105"}
2         local          default          {"root_node_id":"220"}
1         gdrive         work             {"credentials_ref":"..."}
0         functions      system           {"root":"functions"}
0         users          system           {}
1         shared         me               {}
```

Провайдер должен получать уже готовую конфигурацию. Он не должен сам гадать, какому пользователю или подключению она принадлежит.

Чтобы распознать `[user:17]`, когда у пользователя может быть несколько областей ресурсов, нужна таблица областей ресурсов по умолчанию:

```text
principal_default_scopes
  principal_type   // user, org, service, system
  principal_id
  purpose          // default, local, functions, admin
  scope_id
```

Тогда:

```text
local@default[user:17]:///docs/a.txt
  -> распознать область ресурсов user:17 по умолчанию
  -> найти local@default внутри этой области ресурсов

local@default[scope:88]:///docs/a.txt
  -> использовать scope:88 напрямую
  -> проверить ACL перед входом в область ресурсов
```

Точки монтирования тоже должны ссылаться на `scope_id`:

```text
mount_points
  id
  scope_id
  mount_path
  target_uri
  flags
```

Так модель остается чистой:

```text
scopes = пространства ресурсов
provider_connections = экземпляры провайдера внутри области ресурсов
mount_points = человекочитаемые псевдонимы внутри области ресурсов
resource_acl = вся авторизация, включая вход в область ресурсов и управление ей
```

### 20. Путь распознавания

`ResourceResolver` или будущий `VFSRouter` должен владеть логикой маршрутизации, которую текущий `FSManager` смешивает с допущениями о домашнем каталоге.

Цепочка:

```text
1. Разобрать ResourceURI
2. Получить исполнителя из контекста
3. Распознать итоговую область ресурсов:
   - явно указано [user:17]
   - явно указано [scope:88]
   - неявная область ресурсов исполнителя
   - область ресурсов провайдера по умолчанию, например users@system -> system
4. Найти запись области ресурсов
5. Проверить через ACL, что исполнитель может войти в область ресурсов или управлять ей
6. Найти `provider_connections` по провайдеру, подключению и scope_id
7. Распознать идентичность целевого ресурса
8. Проверить через ACL, что исполнитель может выполнить r/w/x над целевым ресурсом
9. Создать или переиспользовать экземпляр FSProvider по конфигурации подключения
10. Вызвать метод провайдера с путем из URI
```

Так VFS превращается из файлового менеджера текущего пользователя в маршрутизатор ресурсов.

Старая модель:

```text
глобальный файловый корень
  /users/42/home
  /users/17/home
```

Новая модель:

```text
корневой путь выводит список доступных областей ресурсов
  /my-343123/
  /project-acme-9981/

выбранная область ресурсов выводит список своих точек монтирования
  /my-343123/home              -> local@default[scope:1]:///
  /my-343123/shared            -> shared@me[scope:1]:///
  /my-343123/cloud/google/work -> gdrive@work[scope:1]:///
```

### 21. Рекомендуемое направление реализации

Начать лучше с маленького конкретного пилота:

```text
UsersFSProvider
```

Он должен открыть:

```text
users@system:///
users@system:///"admin - 1"/
users@system:///"admin - 1"/userdata.json
```

Этот пилот проверит ключевые идеи:

- динамические директории;
- JSON-файлы, которые собираются из сервисов и БД;
- проверка данных при записи;
- операции через файлы действия и `Control`;
- разбор URI;
- поведение, специфичное для провайдера;
- совместимость с существующими VFS-методами.

После этого тот же паттерн можно расширять на:

```text
functions@system:///
shared@me:///
gdrive:///
system@default:///
```

### 22. Главное архитектурное правило

Не нужно превращать файловую метафору во внутреннюю религию.

Использовать VFS стоит как внешний API и интеграционную модель:

```text
снаружи: файлы, каталоги, URI, методы
внутри: сервисы, БД, провайдеры, облачные API, доменная логика
```

Так сохраняется сила подхода, похожего на Unix, без требования, чтобы каждый внутренний модуль притворялся настоящей файловой системой.

### 23. Итоговая позиция

Лучшее направление:

```text
канонический URI начинается с провайдера
пути монтирования работают как псевдонимы
FSProvider задает контракт, похожий на системные вызовы
провайдеры-проекции показывают системные модули как файлы и каталоги
Control выполняет команды провайдера
параметры запроса используются только для декларативных модификаторов
подключения провайдера в контексте для пользовательских облачных аккаунтов
local как провайдер, смонтированный внутри области ресурсов
видимый пользователю корень является пространством имен точек монтирования, а не глобальным корнем
простое пространство имен путей подходит для WebDAV и человеческого просмотра
канонический URI является внутренним адресом для клиентов и сервисов
```

Коротко:

```text
Канонический URI идентифицирует ресурс.
Метод VFS выполняет операцию.
Параметры запроса меняют представление или выборку.
Control выполняет команды провайдера.
Точки монтирования делают навигацию удобной.
Провайдеры сохраняют свою настоящую внутреннюю семантику.
```
